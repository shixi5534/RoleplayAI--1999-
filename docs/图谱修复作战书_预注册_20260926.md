## 2. 代理编制与互相认证协议（核心）

每版本四角色，**修复者永不复核自己**：

1. **Repairer（修复代理）**：读质检报告对应条目 + 灰机（缓存优先，缺口 api.php）+ 语料 grep → 产出 `data/compendium_rag/repairs_v{n}/proposal.json`：每条修复 = {type: split_alias/add_alias/merge_entities/add_entity/remove_alias/reassign_chunk, target, evidence: [灰机URL+拉取时间, chunk_id+原句], before/after}。**不直接写 graph.json**。
2. **Verifier（复核代理，独立）**：不给看 Repairer 的推理，只给 proposal + 同样标准源 → **独立重推正确答案** → 与 proposal 逐条 diff → 三态结论（agree / disagree+反证 / insufficient-evidence）。Verifiers 轮换：R1 的修复者当 R2 的复核者，以此类推。
3. **仲裁**：disagree 条目 → 第三代理只看双方证据投票；再僵持 → 升级用户。
4. **Applier（脚本，非代理）**：`scripts/_graph_apply_repairs.py`（新写）：校验 referential integrity（无悬空 eid/chunk_id、无重名、alias 逐字在语料、mentions==chunk_ids）→ 全部 PASS 才写 `graph.json`；写前 `graph.json.prev.v{n}` 备份，写后重跑质检脚本全部结构检查。

## 4bis. 补录（2026-09-27 #39 复验追加，四条硬规则）

> 触发：R4 声称的「裸检索 +4 题（0.7959→0.8112）」在冷启动下**完全不可复现**（冷跑恒为
> 156/196），根因是 `retriever.py` 的实体链接排序依赖 dict 插入序（详见下）。

1. **落盘后一律冷启动复评，禁止暖进程自评。**
   R4 的评测跑在 Applier 落盘后的**同一进程**里（内存 alias_index 插入序），
   而新会话冷启动自 `graph.json` 重建（文件序），两者不同 → 3 道 300cn + 1 道泛化题翻转。
   **任何"收益"数字必须来自冷启动进程**；暖态数字只能标注为"暖态测量"引用。
2. **别名/实体层变更后一律 rebuild 索引。** 索引与图谱必须同代，且 `rebuild_indexes`
   现已带写前自动备份（`.prev` + `index_backup_manifest.json`）。
3. **排序必须带显式次级键。** `sorted(..., key=len, reverse=True)` 之类的用法
   在 Python 稳定排序下让结果依赖插入序。现已修为 `key=lambda k: (-len(k), k)`，
   并令 `GraphStore.from_dict` 的别名归属确定化（冲突取 eid 字典序最小）。
   实测：修复前 300 题中 **37 题**的 seeds 会随插入序改变；修复后两种插入序完全一致。
4. **入库字节 == 磁盘字节。** 仓库已加 `.gitattributes`（`-text`）禁用 EOL 转换，
   `GraphStore.save` 统一为 `indent=2 + CRLF`，使冻结 SHA 成为可往返验证的锚点。
   **一切以 SHA-16 为准；图内嵌 `fingerprint` 是常量 schema 标记，不作内容判据。**
