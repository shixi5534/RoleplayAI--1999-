## 1. 需求拆解与"最大动作描绘程度"的答案

用户原话（节选）：

> live2d 的本体放在屏幕左边，**根据 live2d 的最大动作描绘程度，来判定 live2d 的相对屏幕位置**

这句话有三种解释，实测后只有一种可行：

| 解释 | 含义 | 实测代价 | 结论 |
|---|---|---|---|
| **(a) 按最大动作留白** | 保证任何动作都不出画 | 314704 需舞台加宽 **1.90 倍**（1080p 716 → 1360px），聊天区只剩 516px | ❌ 不可行 |
| **(b) 按视觉重心区间定相对位置** | 用静止占位 + 动作包络算出"角色视觉重心在哪"，据此定偏移 | **离线算一次，运行时零成本** | ✅ **采用**（最贴近原话"判定相对屏幕位置"） |
| **(c) 动态舞台宽** | 动作大时舞台自动变宽 | `live2d.js:1271-1274` 的 `setZoom` 会连带调 `_fit`，逐帧调用 = 每帧全量重排；且与 `layout.js` 的 `roleplay_layout_split` 持久化打架 | ❌ 强烈不建议 |

**用户已拍板**：允许裁边，舞台按 **1.18~1.24×** 留白，3 个超宽慢动作放行。

### 1.1 动作包络实测（三模型逐动作运行时扫描）

| 模型 | 静止内容宽 | 全动作包络 | 倍数 | 横向占位 x 区间 |
|---|---|---|---|---|
| 314701 | 612.6px | **628.4px** | **1.18×** | [−50.4, +578.0] |
| 314702 | 630.1px | **646.1px** | **1.21×** | [−57.4, +588.7] |
| 314704 | 811.8px | **1010.8px** | **1.90×** | **[−304.0, +706.8]** |

> **重要发现**：**静止内容本身就比画布宽 15%~53%**（314704 是 1.526×）。这不是 bug，是「上半身取景」的设计意图。所以"裁边"其实是**常态**，不是异常。

### 1.2 「8% 余量」是空的（代码宣称 vs 实际）

| 代码位置 | 宣称 | 实际 |
|---|---|---|
| `frontend/js/live2d.js:532-540` `_clampOffset()` | 夹紧拖拽偏移 | **什么都不做**（只做 `isFinite` 归一化，注释明说"按用户要求放开左右与上下边界…不再夹紧"） |
| `frontend/js/live2d.js:626-633` zoom 上限 | 封顶 | **已删**（同段有踩坑记录） |
| `frontend/js/live2d.js:617` `topMargin = Math.round(h * 0.08)` | 8% 余量 | **唯一真实存在的余量，且只作用于竖直顶部** |

⇒ 左右的任何余量**都未实现**。实测：314701/314702 的漂移是 −1.0%~+0.5%（8% 够用），**314704 需 +23.7% ⇒ 差 15.7 个百分点**。

### 1.3 逐动作明细（供定"最大动作"用）

| 模型 | 最大动作 | 时长 | 宽度 | 倍数 |
|---|---|---|---|---|
| 314701 | `b_zhelian` | 9.33s | 628.4px | 1.18× |
| 314702 | `b_zhelian`，**另有 `b_feie` 16.00s / 角度总和 92.35 = 全库最大单动作** | — | 646.1px | 1.21× |
| 314704 | **`b_gongsheng`**（AngleX 52.20 + AngleY 51.39 双第一） | 9.67s | 1004.2px | 1.237× |

314704 逐动作宽度：`b_gongsheng` 1004.2 / `b_huashu` 960.3 / `b_idle` 937.8 / `b_huazhang` 913.0 / `b_diantou` 831.7 / 其余 6 个 735.2~829.6（0.906~1.022×）。

**motion3 参数并集（三模型）**：

| 参数 | 314701 | 314702 | 314704 |
|---|---|---|---|
| `ParamAngleX` | −9.55 .. 30.00（跨度 39.55） | 同 314701 | **−22.20 .. 30.00（跨度 52.20）** |
| `ParamAngleY` | −18.07 .. 11.20 | −29.52 .. 13.83 | −30.00 .. 23.00 |
| `ParamBodyAngleX` | −8.94 .. 9.00 | −20.29 .. 9.00 | **无此曲线** |
| 自定义 `ParamNN` | 163 个动作中 112 个有 | 153 个 | **189 个中 182 个有** |

两处纠正（重要，之前文档写错了）：
1. `ParamAngleX` 最小值**不是 0**，是 −9.55 / −22.20。
2. 「314704 的 `ParamAngleX` 只有 0..1」**是误读**——全模型并集是 −22.20..30.00，**幅度被低估 50 倍**。`0..1` 只出现在 `t_*` 表情动作里，而**所有 `t_*` 表情动作的角度跨度恒为 0.00**。

### 1.4 「8% → 实际需要」的量化结论

| 模型 | 需加宽 | 用户批的 1.18~1.24× 够不够 |
|---|---|---|
| 314701 | 1.18× | ✅ 正好 |
| 314702 | 1.21× | ✅ 够 |
| 314704 | 1.90×（全部）／**1.237×（去掉 `b_gongsheng` 后）** | ✅ 按 1.24× 留白 + **放行 `b_gongsheng` 一个超宽动作** |

⇒ 落地：`_fit` 的 `maxW = w * 1.6 * ratio`，`ratio` 按模型取 `1.00 / 1.01 / 1.24`。

### 1.5 建议新增的数据文件（离线生成，运行时只读）

`frontend/assets/live2d/motion_envelope.json`：

```json
{
  "314701": {
    "restW": 612.6, "envelopeW": 628.4, "maxAction": "b_zhelian",
    "safeW": 620.0, "outliers": [],
    "xRange": [-50.4, 578.0], "centroidX": 0.5
  },
  "314704": {
    "restW": 811.8, "envelopeW": 1004.2, "maxAction": "b_gongsheng",
    "safeW": 828.0, "outliers": ["b_gongsheng"],
    "xRange": [-139.9, 703.4], "centroidX": 0.47
  }
}
```

字段含义：
- `restW`：静止内容宽（px，基于基准视口）
- `envelopeW`：全动作最大宽
- `maxAction`：产生最大宽的那个动作名
- `safeW`：**92% 分位宽**（丢掉离群动作后的安全值）
- `outliers`：离群动作名（放行）
- `xRange`：内容横向占位区间
- `centroidX`：视觉重心（0~1，相对画布宽）—— **这就是"相对屏幕位置"的权威依据**

## 3. Live2D 本体放左边

### 3.1 好消息：不用改 `_fit`

`_clampOffset()`（`frontend/js/live2d.js:532-540`）现在**什么都不做**，所以"放左边"只是**给 `model_offset.x` 一个默认负值**。

### 3.2 落地做法

| 步骤 | 位置 | 做法 |
|---|---|---|
| 1 | `frontend/js/chat.js:129` `model_offset: { x: 0, y: 0 }` | 默认值改为 `-0.18 * 舞台宽`（约 −129px @1080p） |
| 2 | `frontend/js/chat.js:134` 读 localStorage | **加 `version` 字段**，老版本 `roleplay_ui_state.model_offset` 直接清掉（否则老用户被旧偏移卡住） |
| 3 | 按动作幅度插值 | 314701 → `−0.12W`；314702 → `−0.14W`；**314704 → `+0.06W`**（因为它只往左偏，重心已偏左，再左移会切脸） |
| 4 | 持久化 | 用户手动拖拽后仍以用户值为准，`version` 升级只清一次 |

**为什么 314704 要往右？** 它的内容横向占位是 [−304.0, +706.8]，重心 `centroidX = 0.47`（偏左）。默认再左移会导致左侧脸部被切。这是"按视觉重心定位置"的直接应用。

### 3.3 不做的事

- ❌ 动态舞台宽（见 §1 解释 (c)）
- ❌ 改 `#live2d-canvas` 的 id（全仓 9 处引用，无收益）
- ❌ 改 `filter: drop-shadow(...)`（`frontend/css/index.css:394-396`，**这是整站唯一受光来源**，经 4 轮 A/B 定档）

## 5. 历史消息三形态（H1/H2/H3）

### 5.1 用户拍板（原话）

> `1，2，3都要，长的留在柜子里，3到5以半透明，颜色要渐变`

+ 第二轮追问确认「颜色渐变」= **按新旧：越早越淡**。
+ 第三轮确认阈值：**3 条完整 + 2 条预览 + 其余进抽屉**（D18）。

### 5.2 阈值规格

| 位置（从最新往前数） | 显示 | 不透明度 | 形态 |
|---|---|---|---|
| 第 1 条 | 完整 | **1.00** | 全文 |
| 第 2 条 | 完整 | **0.82** | 全文 |
| 第 3 条 | 完整 | **0.64** | 全文 |
| 第 4 条 | **预览** | **0.46** | 首行 + 「…」 |
| 第 5 条 | **预览** | **0.30** | 首行 + 「…」 |
| 第 6 条起 | 不显示 | — | 全进抽屉 |

**单条气泡超 120 字** ⇒ 自动折叠成「展开」（`--line-clamp: 3`）。

> 不透明度用 `1 - (n-1) * 0.18`，`n` 从 1 数到 5。不是线性到 0——第 5 条还有 0.30，仍可辨认。

### 5.3 实现要点

```css
/* 用 :nth-last-child 而不是逐条加 class，避免 JS 改 DOM */
#messages > .msg:nth-last-child(1) { opacity: 1; }
#messages > .msg:nth-last-child(2) { opacity: .82; }
#messages > .msg:nth-last-child(3) { opacity: .64; }
#messages > .msg:nth-last-child(4) { opacity: .46; }
#messages > .msg:nth-last-child(5) { opacity: .30; }
#messages > .msg:nth-last-child(n+6) { display: none; }
```

- **纯 CSS 实现**，JS 只负责"进抽屉时把被隐藏的消息搬过去"（或用 `:nth-last-child` 判断后 clone）。
- 「展开」按钮需要 JS，只在超 120 字时插入。
- `prefers-reduced-motion` 下不做过场，直接切。

### 5.4 抽屉内容

抽屉里是**完整历史**（不截断、不降透明度），复刻现有 `#messages` 的渲染。滚动位置独立。

## 6. 屏幕四周装饰

### 6.1 用户拍板

### 6.2 为什么不能用现有两层

### 6.4 为什么是 2D 而不是 WebGL

`docs/canvas-layer-design.md:235` 有一条风险记录：「画布复用同一 PIXI Application 的 container，**不新建 canvas**」。

## 7. 鳞粉粒子

### 7.1 现有"鳞粉"不是粒子（重要认知）

`frontend/js/canvas-fx.js:233-259` 里的鳞粉是**烘焙进 96×96 精灵的静态亮点**（每翅 26+5 颗，固定 LCG 随机，L237-243 是 LCG，L244/L252 两个循环）。它们：

- 不脱落
- 无生命周期
- **每帧成本 0**（已在精灵里）

⇒ 要做"飘散"，**必须新建粒子数组**，不能改烘焙。

### 7.2 现有帧成本（实测）

| 项 | 成本 |
|---|---|
| 固定成本（灯 + 光池 + 光锥 + 15 只蛾） | **2.2~3.8 ms/帧** |
| 420 颗尘（`frontend/js/canvas-fx.js:47 var DUST_N = 420;`） | **7.0~7.4 ms（65~78%）** |
| **合计** | **9.2~11.2 ms** |

最小二乘拟合：**1.5~1.8 ms / 100 粒子 / 帧**（取 1.65 做预算）。

**每帧 1414 次 2D 调用**，分布极不均匀：

| 来源 | 调用数 | 占比 | 实际耗时占比 |
|---|---|---|---|
| `drawLampHardware` | 820 | 58% | **~20%** |
| 尘 | 412 | 29% | **65~78%** |

⇒ **优化必须按时间，不按 op 数。** 砍 `drawLampHardware` 的调用数是无效优化。

### 7.3 鳞粉参数（D13 已批总预算）

| 参数 | 值 | 说明 |
|---|---|---|
| `FLAKE_N` | **240**（范围 200~280） | 每颗 1.65ms/100 ⇒ ≈4.0 ms |
| `DUST_N` | **420 → 260**（D13） | 省出 ≈2.6 ms |
| 寿命 τ | 7~12 s，均值 9.5 s | — |
| 发射率 | 25.3 颗/s | `FLAKE_N / τ` |
| 初速 | 18~42 px/s | 慢到"悠悠" |
| `s0` 半径 | **1.2~3.8 px** | **必须比尘（0.68~10.2 px）小**——这是"比光粉小"的量化 |
| 末端半径 | `0.28 × s0` | 体积递减 |

**总账**：`260 颗尘 (≈4.3ms) + 240 鳞粉 (≈4.0ms) + 固定 3.0ms = 11.3 ms` < 16.7ms（60fps 预算）。✅

### 7.4 物理与生命周期公式

用户要求「用函数来实现变化」，所以**全部闭式，可单测**：

```
p    = age / life                          // 0 → 1 归一化进度
alpha = a0 * pow(1 - p, 1.8)               // p>0.70 时 alpha<0.02（"溶入"判据）
s(p)  = s0 * (1 - 0.72 * pow(p, 1.4))      // p=1 时 0.28 * s0
v(p)  = v0 * (1 - 0.60 * p)                // 越飘越慢
```

**"溶入屏幕"的判据**（三条同时满足即回收）：
1. `p > 0.70` 且 `alpha < 0.02`
2. 颜色与模型主色的 OKLab 距离 `< 0.02`
3. 越界（出画布）

> ⚠️ **`.stage` 有 `overflow: hidden`**（`frontend/css/index.css:318`）。舞台内粒子贴边会被**裁掉**而不是"溶入"。修法：`距边 < 8%` 时强制 `p = max(p, 0.85)` 提前溶掉。
> 整屏层（§6.3）不受此限，可以真的飘出屏幕。

### 7.5 风场（闭式正弦叠加，零预计算）

全仓 grep `wind|flow|noise|perlin|simplex|curl|风|湍` **零命中**——现在没有风场。现有"飘动"是三项互不相关的独立随机：
- 尘：`off += gauss() * 3.5 * dt`（`:763`、`:769`）
- 蛾：`ax += cos(t*0.21+ang0) * 8 + gauss() * 24`（`:667-668`）
- 光锥：`sway = sin(t*0.13) * 0.035`（`:999`）

新增风场（**可单测、零预计算、同参必同值**）：

```js
var WIND_BASE_ANG = -0.55, WIND_BASE_MAG = 16;
function windAt(x, y, t) {
  var u = x / W, v = y / H;
  var a = Math.sin(v * 5.4 + t * 0.31);
  var b = Math.sin(u * 6.9 - t * 0.19 + 1.7);
  var c = Math.sin((u + v) * 11.3 + t * 0.83);
  var ang = WIND_BASE_ANG + 0.42 * (a + b) + 0.13 * c;
  var mag = WIND_BASE_MAG + 7.5 * (a + b) + 2.2 * c;
  return [Math.cos(ang) * mag, Math.sin(ang) * mag];
}
```

成本：240 颗 × (3 sin + 1 cos) ≈ **0.02 ms/帧**。可忽略。

### 7.6 颜色插值（**不能写死三模型颜色**）

三模型主色实测色相相差约 **190°**：

| 模型 | 主色 | 点缀色 | 有彩占比 |
|---|---|---|---|
| 314701 | `#272B5F`（靛蓝） | `#2C2D9F` | 35.5% |
| 314702 | `#3C3D5D`（深蓝灰） | `#C4AD74` | 5.6% |
| 314704 | `#5B5334`（橄榄褐绿） | `#AAAC83` | 7.0% |

亮黄端取 **`#FFB46B`** —— `frontend/js/canvas-fx.js:1212` 注释原文：「真实白炽灯的色温是 (255,180,107) 量级」。

**必须用 OKLab 插值，不能用 RGB 线性插值**：

| 插值空间 | t=0.5 处结果 |
|---|---|
| RGB | 脏玫瑰 `#BD8579`（发灰发脏） |
| **OKLab** | **紫灰 `#877188`**（自然过渡） |

附加规则：
```
chroma *= (1 - 0.55 * u)
u = smoothstep(0.15, 0.85, p)
```

**性能**：预烘 **32 级色带查表**，运行期零转换成本。

### 7.7 开关（现有代码没有）

`?fx=off` **不存在** —— `frontend/js/canvas-fx.js` 里 `URLSearchParams` / `location.search` 均 0 命中。

现在唯一的"关"法是系统级 `prefers-reduced-motion` 只画一帧静帧（`:1774-1778`）。

⇒ 新增粒子层**必须自带开关**：
- URL 参数 `?fx=off`（关整屏装饰层）
- URL 参数 `?flakes=0`（只关鳞粉，留尘）
- `prefers-reduced-motion` 尊重（已有机制）

## 8. 丁达尔体积光（D03）

D03 确认「叮当而效应」= **丁达尔效应 = 光柱/体积光**。

### 8.1 现有实现与问题

`frontend/js/canvas-fx.js` 的 `drawCone`（`:1006 var steps = 40;`，注释「段数少了会看到明显的梯形台阶」）每帧画 40 段：

- 40 次 `createLinearGradient`
- 160 次 `lineTo`

这是**每帧重画一个形状几乎不变的锥体**（只有 `sway = sin(t*0.13) * 0.035` 慢摆，`:999`）——纯粹的浪费。

### 8.2 方案成本排名（`_micro2.json` 实测，flush 后相对基线）

| 排名 | 方案 | 成本 | 相对倍数 |
|---|---|---|---|
| 🥇 | **③a 离屏半分辨率光板 + 1 次 drawImage** | **3.10 ms** | **15× 最省** |
| 2 | ② 噪声滚动全屏 | 8.40 ms | — |
| 3 | ③a 升采样全屏 | 8.60 ms | — |
| 4 | ① 径向渐变 K=8 | 26.5 ms | — |
| 5 | ① 径向渐变 K=16 | 41.4 ms | — |
| 6 | ① 径向渐变 **K=32**（现有 `drawCone` 走的路） | **47.1 ms** | — |
| 7 | 粒子 500/1000/1500/2000/3000 | 31.8 / 71.6 / 92.7 / 138.8 / 185.2 ms | — |
| 8 | ④ `ctx.filter` | **149.6 ms** | ❌ 永久封杀 |

**推荐 = 离屏半分辨率光板 + 噪声 1 次 `drawImage`**（3.10 ms）。

### 8.3 `ctx.filter` 永久封杀（两条独立证据）

| 证据 | 内容 |
|---|---|
| 实测 | `blur(8px)` 单次 400×400 = **149.6 ms/帧** |
| 代码注释 | `frontend/js/canvas-fx.js:52` 原文：「实测把帧率压到 0.4fps」 |

⇒ 任何涉及 `ctx.filter` 的方案一律否决。

### 8.4 落地做法

1. 光锥形状**预烘到离屏 canvas**（半分辨率），只在 `sway` 变化超过阈值时重建，否则复用。
2. 每帧只做 **1 次 `drawImage`** 把光板贴到主画布。
3. 丁达尔噪声用 `frontend/assets/live2d/wmz/314702/textures/noise_077_tps.png`（512²）滚动叠加，同样走 `drawImage`。
4. 省下的 ≈44 ms（47.1 → 3.1）**远超**鳞粉的 4.0 ms 开销 ⇒ **D13 的"尘 420→260"其实可以不做**，但用户已批，两笔都记着，实现时取更宽松的。
