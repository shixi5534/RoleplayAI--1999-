## 摘要（5 条核心结论）

1. **当前"点了长时间没反应"不是浏览器限制，而是自家冷却参数 + 冷却期静默反馈的结果。** `pet-voice.js` 的 `SLOT_COOLDOWN_MS = 25s` 且从音频**自然结束**时刻起算：click 槽中位时长 5.2s，即一次点击后约 **30 秒**内同槽位静默 `return null`，且**无任何视觉/听觉反馈**。这不是规范要求，25s 这个数字在本项目里也没有依据。【判断 + 代码事实】

2. **自动播放策略对本项目几乎不构成威胁，但必须按规范写错误处理。** 本项目所有播放都由 `click` 事件同步发起，Chrome/Safari/Firefox 三家（含最严格的 Safari）在"用户已点击过该页面"后都会放行。真正需要做的是：**永远处理 `play()` 返回的 Promise**，并在被拒时清理状态（Chrome 官方明确要求）。【厂商：developer.chrome.com、webkit.org】

3. **重复点击策略应选「带保护期的打断（interrupt with grace）」，而非排队或无视。** 依据：Apple 官方"用户把 UI 元素当作真实物体、期待即时反应"的准则；语音助手行业通用的 barge-in（打断）范式与配套参数（Grace 200–1000ms / Debounce 250–750ms / Cooldown 500–1500ms）；排队会造成"反馈与操作脱节"（Nielsen：超过 1s 用户即失去"直接操纵"感）。【厂商 + 业界 + 判断】

4. **冷却（cooldown）的目的应是"内容去重"而非"静音窗口"。** 本项目 click 槽中配池只有 5 段，靠 25s 时间窗防重复既粗暴又伤害体验；改用**洗牌袋（shuffle bag）一轮内不重复** + **1.5s 播后静默间隔**，可同时满足"不刷屏"与"点了有反应"。1.5s 取自语音助手行业 Cooldown 预设的上沿值。【业界 + 判断】

5. **必须补三件工程"保险"：状态机看门狗、单 `<audio>` 实例复用、冷却期可见反馈。** 现有代码存在 `audio` 引用可能永久残留（导致所有非 click 槽位永久静默）、每次 `new Audio()` 且 `stop()` 不释放 `src`、冷却期完全无反馈三个隐患。Web Audio 全量预解码在本项目**不可行**（双语音约 755s 音频，解码为 Float32 PCM 约 146MB @48kHz）。【判断 + 计算】

## 0. 本项目现状诊断（读代码 / 读素材所得事实）

> 本节为代码事实与数据推导，**非**外部规范结论，但它是后续所有建议的落点。

### 0.1 素材实测数据

从 `manifest.json` 统计（含 `dur` 字段）：

| 槽位 | id 数 | 中配段数 | 中位时长 | 最长 |
|---|---|---|---|---|
| enter | 3 | 1 | 9.6s | 9.6s |
| **click** | 12 | **5** | **5.2s** | 6.2s |
| happy | 15 | 5 | 6.7s | 12.2s |
| sad | 15 | 5 | 5.6s | 10.2s |
| surprise | 5 | 2 | 6.2s | 7.7s |
| sleep | 5 | 2 | 7.0s | 10.3s |
| idle | 20 | 7 | 7.3s | 12.3s |
| intel | 7 | 3 | 4.4s | 7.3s |
| **battle** | 13 | 2 | **37.2s** | **62.6s** |

中配合计 48 段 / 380.6s（中位 5.8s，P90 11.8s，最大 62.6s）；英配 85 段 / 374.3s（中位 3.5s）。

**两个关键事实**：
- **click 槽中配只有 5 段**。随机播放时连点极易重复 → 内容去重的优先级高于时间冷却。
- **battle 槽存在 62.6s 的长片段**。播放期间 `playForSlot()` 开头的 `if (audio && !audio.ended) return null` 会**阻塞除 click 外的所有槽位长达一分钟以上**；且 62 秒的语音没有任何"停止"入口。

### 0.2 `pet-voice.js` 的三个可复现问题

**问题 A —— 25s 冷却从"播放结束"起算，造成约 30s 静默窗口（主因）**

```js
const SLOT_COOLDOWN_MS = 25 * 1000;
a.onended = () => { ...; lastPlayedAt[slot] = Date.now(); }   // 冷却从结束起算
...
const last = lastPlayedAt[slot] || 0;
if (Date.now() - last < SLOT_COOLDOWN_MS) return null;        // 静默 return，无反馈
```

click 槽中位 5.2s → 一次点击后 **5.2 + 25 ≈ 30.2s** 内再次点击完全无响应。这与用户实测反馈"点击后能播放一段语音，但随后很长一段时间内再次点击无法重新触发"完全吻合。

**问题 B —— `audio` 引用可能永久残留，导致非 click 槽位永久静默**

`audio` 只在三处被置空：`onended`、`onerror`、`play()` 被拒的 `catch`。若音频出现 **stall（缓冲耗尽但既不 `ended` 也不 `error`）**、`stop()` 路径（切语言 / TTS 抢占 / 静音）后残留、或 `onended` 因 `loop`/异常未触发，`audio` 将长期非 null 且 `ended === false`，于是：

```js
if (audio && !audio.ended) {   // 非 click 槽 → 直接 return null
  if (slot === "click" && audio.currentTime > 2) { /* 打断 */ }
  return null;
}
```

所有非 click 槽位被永久锁死。**现有代码没有任何看门狗（watchdog）兜底。** 相应地，`stop()` 路径也不写 `lastPlayedAt`，导致"被打断不进入冷却、自然播完才进入冷却"的不一致。

> 补充事实【厂商】：MDN 对 `ended` 的定义是"playback or streaming has stopped **because the end of the media was reached or because no further data is available**"——注意后半句，`ended` 会在数据断流时触发，因此 stall 末尾大概率会 `ended`；但 `loop === true` 时**不会**触发，且 `pause()` 明确不触发 `ended`。
> 来源：<https://developer.mozilla.org/en-US/docs/Web/API/HTMLMediaElement/ended_event>

**问题 C —— 冷却期内"零反馈"**

冷却命中时 `playForSlot()` 直接 `return null`，不发任何事件、不切换任何 UI 状态、不播任何提示音。用户侧的主观体验就是"程序坏了"。**规范上，这是最需要修的一点：把"冷却"和"无反馈"解耦。**

### 0.3 已有的一处正确做法（保留）

`live2d.js:760` 已有 `if (now - this._lastClickAt < 800) return;` 的连点防护，且在**发出 intent 之前**生效，因此不会与 `pet-voice.js` 的冷却叠加成更长的静默窗口。这个 800ms 偏保守但方向正确（第 3 章会给出建议值）。

## 1. 浏览器自动播放策略（Autoplay Policy）

### 1.1 Chrome / Edge

【厂商】Chrome 官方规则原文：

- 「Muted autoplay is always allowed.」
- 「Autoplay with sound is allowed if: **The user has interacted with the domain (click, tap, etc.)** ／ 在桌面端用户的 **Media Engagement Index (MEI)** 已越过阈值 ／ 用户把站点加到主屏或安装了 PWA ／ 顶层框架通过 Permissions Policy 把权限委派给 iframe。」
- 不满足时，`play()` 返回的 Promise 以 **`NotAllowedError`** 拒绝，`autoplay` 属性被忽略。

MEI 的计量口径（官方原文）：媒体消费时长 > 7 秒、音频存在且未静音、标签页处于活动状态、视频尺寸 > 200×140 px。

来源：<https://developer.chrome.com/blog/autoplay/>

**对本项目的含义【判断】**：`pet.html` / `index.html` 的语音全部由 `click` 事件同步发起，且用户必然已与页面交互过 → **走的是"用户与域交互过"这条放行路径，与 MEI 无关，几乎不会遇到 `NotAllowedError`**。但这不能成为不写错误处理的理由：Chrome 企业策略、Permissions Policy、用户手动关闭音频权限都会让 `play()` 被拒。

**Chrome 官方对 Web 开发者的要求（原文直译）**：

> 「切勿假定视频会播放，并且在视频实际上未播放时不要显示暂停按钮。……您应始终查看 `play` 函数返回的 Promise，以了解它是否被拒绝。」

### 1.2 Safari / WebKit（最严格）

【厂商】WebKit 官方博客（macOS 自动播放策略变更）：

> 「**Websites should assume any use of `<video>` or `<audio>` requires a user gesture click to play.**」
> 「Don't assume a media element will play, and don't show the pause button from the start. Look at the Promise returned by the `play` function on `HTMLMediaElement` to see if it was rejected.」
> 「**Auto-play restrictions are granted on a per-element basis. Change the source of the media element instead of creating multiple media elements** if you want to play multiple videos back to back.」

来源：<https://webkit.org/blog/7734/auto-play-policy-changes-for-macos/>

iOS 侧：<https://webkit.org/blog/6784/new-video-policies-for-ios/> 明确"用户手势"指的是 `touchend` / `click` / `doubleclick` / `keydown` 的处理器**直接**触发的 JS。

**⚠️ 一条对本项目极其重要的 Safari 差异**【厂商，已确认的 WebKit Bug】：

> 「unlike other browser engines, **Safari will only permit the `play()` call from the synchronous scope of an event handler**. Consequently it is not possible to implement asynchronous handling of playback.」

来源：<https://bugs.webkit.org/show_bug.cgi?id=259925>（WebKit Bug 259925，状态 NEW）

**工程含义【判断】**：**点击处理函数里，在第一个 `await` 之前必须完成 `audio.play()` 的调用**。当前 `pet-voice.js` 的 `playClip()` 是同步的，符合；`voice.js` 的 `speak()` 是先 `await fetch(TTS)` 再 `play()`，**在 Safari 上第一次调用会被拒**（除非页面已有 sticky activation，实际桌面 Safari 通常已放行，但移动端 Safari 风险实存）。这条必须写进工程师的检查清单。

### 1.3 Firefox

【厂商】MDN 记录的 Firefox 相关首选项（说明其模型也是"sticky activation"级别）：

- `media.autoplay.default`：0=允许 / 1=阻止 / 2=使用时询问，**默认 0**
- `media.autoplay.block-webaudio`：默认 `true`，「audio contexts are only able to play on pages once there has been **Sticky activation**」
- `media.block-autoplay-until-in-foreground`：默认 `true`，后台标签页不自动播放
- `media.autoplay.allow-muted`：默认 `true`

来源：<https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Autoplay>

### 1.4 "用户激活"的正式定义（WHATWG HTML）

【标准】HTML Living Standard §6.4 Tracking user activation：

- **Sticky activation（粘性激活）**：「This is W's historical activation state, indicating whether the user has ever interacted in W. It starts false, then changes to true (**and never changes back to false**) when W gets the very first activation notification.」
- **Transient activation（瞬时激活）**：「indicating whether the user has interacted in W recently. This starts with a false value, and remains true **for a limited time** after every activation notification.」
- **Transient activation duration**：「is expected be **at most a few seconds**, so that the user can possibly perceive the link between an interaction with the page and the page calling the activation-gated API.」
- API 分四类：sticky-gated / transient-gated / transient-consuming / history-action-consuming。
- 可用 `navigator.userActivation.hasBeenActive`（sticky）与 `navigator.userActivation.isActive`（transient）读取。

来源：<https://html.spec.whatwg.org/multipage/interaction.html#tracking-user-activation>

**关键判断【判断】**：媒体播放在各家实现里基本挂在 **sticky activation** 级别（Chrome 的"用户与域交互过"、Firefox 的"sticky activation"），**一次点击即可永久解锁该页面**。所以：

- 不需要"攒够几次点击"或"预热 AudioContext"之类的技巧；
- 但**页面首次加载后的第一次 `play()` 若不在手势里，会被拒** —— 这就是为什么 `enter`（初见）槽位不能直接自动播。

**可选增强（P2）**【厂商】：`navigator.getAutoplayPolicy("mediaelement")` 返回 `allowed` / `allowed-muted` / `disallowed`，可在页面加载时预判。MDN 标注为 **Experimental**，需做特性检测。
来源：<https://developer.mozilla.org/docs/Web/API/Navigator/getAutoplayPolicy>

### 1.5 被拒绝后的正确处理（必须实现）

【厂商】Chrome 官方（两篇）：

> 「never assume that a media element will play. Look at the Promise returned by the play function to see if it was rejected.」

以及关于 `AbortError` 的经典坑：

> `video.play(); video.pause();` → `Uncaught (in promise) DOMException: The play() request was interrupted by a call to pause().`
> 同理 `video.load()` 或 `video.src = ''` 会产生 `The play() request was interrupted by a new load request.`
> 官方建议：把 `play()` 的 Promise 存下来，**在 `then()` 里才 `pause()`**；或用 `load()` 预取、稍后再 `play()`。

来源：<https://developer.chrome.com/blog/play-request-was-interrupted>

**对本项目的直接推论【判断】**：

- 现代码 `stop()` 里直接 `audio.pause()`，**在 `play()` 的 Promise 尚未 resolve 时调用就会抛 `AbortError`**（打日志但不致命）。由于本项目是"打断式"交互，这个错误**无法完全避免**，正确做法是：捕获并**静默忽略 `AbortError`**（`voice.js` 的 `friendlyPlaybackError()` 已经这么做了，`pet-voice.js` 应统一）；
- 若改为"复用单个 `<audio>` + 切 `src`"，每次切 `src` 都会触发 load 算法，也会中断上一次 `play()`，同样的处理即可；
- 另有一条 Chrome 官方警告：**用 `<source>` 子元素时，play() 的 Promise 永不 reject**（"危险区域"章节）。本项目用 `new Audio(url)` 直接给 `src`，**不踩这个坑，但要保持**。

### 1.6 `play()` 返回值与异常清单

【厂商】MDN `HTMLMediaElement.play()`：返回 Promise，成功开始播放时 resolve；失败时以 `DOMException` 拒绝：

- `NotAllowedError`：UA/OS 不允许在当前上下文播放（Permissions Policy、自动播放策略）
- `NotSupportedError`：媒体源格式不受支持

MDN 同时提示：「The `play()` method may cause the user to be asked to grant permission to play the media, resulting in a possible delay before the returned promise is resolved. **Be sure your code doesn't expect an immediate response.**」
来源：<https://developer.mozilla.org/en-US/docs/Web/API/HTMLMediaElement/play>

**工程含义【判断】**：`play()` resolve 之前不能认为"已经在播"。字幕/动画的"播放中"状态应以 **`playing` 事件**（而非 `play()` 调用）为准——`pet-voice.js` 已经监听了 `onplaying`，做法是**正确**的，应保留并向 `voice.js` 推广。

## 2. Web Audio / 音频元素状态机与生命周期

### 2.1 状态机建模：该信哪些信号

| 信号 | 语义（来源） | 能否作为"播放结束"依据 |
|---|---|---|
| `play()` Promise resolve | 播放已**开始**（MDN） | 否（只是开始） |
| `playing` 事件 | 真正开始出声 | 用于"开始播放中"UI |
| `ended` 事件 | 「playback or streaming has stopped because the end of the media was reached **or because no further data is available**」（MDN） | **主依据**，但需兜底 |
| `paused === true` | 已暂停 | 否（`pause()` 不触发 `ended`） |
| `error` / `onerror` | 加载或解码失败 | 是（异常终态） |
| `readyState` | 0 NOTHING / 1 METADATA / 2 CURRENT_DATA / 3 FUTURE_DATA / 4 ENOUGH_DATA（MDN） | 否（只反映缓冲） |

来源：
- `ended` — <https://developer.mozilla.org/en-US/docs/Web/API/HTMLMediaElement/ended_event>
- `readyState` — <https://developer.mozilla.org/en-US/docs/Web/API/HTMLMediaElement/readyState>

**MDN 明确的一条坑**：`ended` 在 `loop === true` 且 `playbackRate` 非负时**不会触发**。本项目 `loop=false`，安全，但值得写进注释。

**推荐的显式状态机【判断】**（本项目可直接照抄）：

```
IDLE ──request──> LOADING ──playing事件──> PLAYING ──ended──> IDLE (记 lastPlayedAt)
  │                  │                       │
  │                  ├──error/stall超时───────┤
  │                  └──play() reject────────┘
  └──任何状态──> stop()/reset() ──> IDLE（必须无条件清除 audio 引用）
```

四条硬性规则【判断，部分有来源支撑】：

1. **终态必须唯一收敛**：`ended` / `error` / `play()` reject / `stop()` / 看门狗超时 **五个出口都要**把 `audio` 置空 + 清定时器 + 写冷却时间戳。缺一个就会复现"问题 B"。
2. **必须加看门狗**：以 manifest 里的 `clip.dur * 1000 + 2000ms` 作为超时上限，超时强制 reset。理由：`ended` 依赖网络与解码，不能假设它一定来；业界同类系统也强调"处理锁必须无条件释放，否则永久锁死"。【业界】参考：<https://os.maria-code.ai/blog/sentence-level-streaming-vui-architecture>（"The flag is unconditionally cleared … preventing permanent lockout from unhandled exceptions"）
3. **`pause()` 不等于结束**：`stop()` 走 `pause()` 路径不会触发 `ended`，需**主动**写冷却时间戳、主动广播 `stopped` 事件。
4. **代际令牌（generation token）防竞态**：`voice.js` 的 `speakGen` 与 `micGen` 是正确示范；`pet-voice.js` 用 `audio === a` 做身份校验也是等价做法，应保留。

### 2.2 `new Audio()` 频繁创建 vs 复用实例

**权威意见（明确支持复用）**【厂商】：

- WebKit 官方博客：「**Change the source of the media element instead of creating multiple media elements**」—— <https://webkit.org/blog/7734/auto-play-policy-changes-for-macos/>
- WebKit 官方博客补充：「Auto-play restrictions are granted on a **per-element basis**」——同上。**创建新元素意味着丢失已获得的播放许可，这正是本项目在 Safari 上最可能翻车的点**：每次 `new Audio()` 都是一个全新元素，需要重新判定自动播放许可。这是改用单实例的**最强技术理由**。

**业界实测与经验**【业界】：高频点击场景下每次 `new Audio()` 会重复发起网络请求、重复解码、堆积未释放的音频资源，导致页面卡顿与音效延迟（见 <https://m.php.cn/faq/2889481.html>）；游戏场景下的通用做法是维护一个 Audio 元素池，播放完毕后复用（见 Stack Overflow `Better way to call new Audio()`，<https://stackoverflow.com/questions/67445712/better-way-to-call-new-audio>）。

**本项目应采用的方案【判断】**：

> **方案 A（P0，推荐）：复用 1 个 `<audio>` 元素 + 切 `src`，最多 2 个（一个"当前"、一个"预取下一候选"）。**

理由链：
1. WebKit 官方明确要求换 src 而非建新元素（见上）；
2. Safari 的自动播放许可是 per-element 的，复用 = 一次解锁、长期有效；
3. 内存 O(1)，不会像 `new Audio()` 那样堆积已下载缓冲；
4. 改造量最小：`stop()` 里除 `pause()` 外补 `audio.removeAttribute('src'); audio.load();` 即可释放缓冲。

**方案 B（P2，可选）：Web Audio 预解码。** 结论：**本项目不宜全量采用**。

- MDN 对 `AudioBuffer` 的定义：「designed to hold small audio snippets, **typically less than 45 seconds**」—— <https://developer.mozilla.org/en-US/docs/Web/API/AudioBuffer>（单条片段长度是合适的，本项目中位 5.8s）；
- 但**总量算不过来**【计算】：中配 380.6s + 英配 374.3s ≈ 755s。解码为 Float32 PCM（AudioContext 典型采样率 44.1/48 kHz）后约 `755 × 48000 × 4B ≈ 145 MB`；即使降到 24 kHz 也要约 72 MB。**对桌面宠物常驻页面而言不可接受。**
- 折中：仅对 **click 槽**（最常触发、中配 5 段共约 21s）做小池预解码，约 `21 × 48000 × 4 ≈ 4 MB`，用于消除首帧延迟。属于锦上添花，非必需。

### 2.3 预加载与缓存

`preload` 属性值语义【厂商，MDN】：

- `none`：不预加载
- `metadata`：只取元数据（时长等）
- `auto`：可整文件下载
- 空字符串 = `auto`
- **「The default value is different for each browser. The spec advises it to be set to `metadata`.」**
- 注意：「The browser is not forced by the specification to follow the value of this attribute; **it is a mere hint**.」

来源：<https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/audio>

**本项目建议【判断】**：

| 对象 | 策略 | 理由 |
|---|---|---|
| 复用的 `<audio>` 元素 | `preload = "auto"` | 单实例，无并发下载压力；保证切 src 后尽快可播 |
| 候选池其余片段 | 不预加载，靠 HTTP 缓存 | 中配 48 段共约 3MB，首轮点完基本已入 HTTP 缓存；主动预取 6MB 会拖慢首屏 |
| 下一个候选片段 | 空闲时用第 2 个 `<audio>` 预热（`preload="auto"` 或 `fetch` 后 `URL.createObjectURL`） | 命中率有限、实现复杂，**列为 P2** |
| manifest.json | 现状 `cache: "no-store"` → 建议改回默认（走 ETag / 短 Cache-Control） | 现状注释写的是"P1-11 禁用缓存"，但 manifest 带 `version` 字段，改用 `?v=<version>` 即可兼顾实时性与缓存【判断】 |

**关于 `<audio>` 的 `loop`**：本项目不用，且 MDN 警告 `loop` 会让 `ended` 不触发——保持 `loop = false`。

## 3. 节流（throttle）/ 防抖（debounce）/ 冷却（cooldown）

### 3.1 三者的定义与适用边界（业界共识）

【业界】多家技术站点的表述高度一致：

- **Debounce（防抖）**：延迟到"最后一次调用后 N ms"才执行；期间每次新调用都重置计时器。**"等到停下再做一次"**。适用：搜索联想、自动保存、resize 结束、表单校验。
- **Throttle（节流）**：在一个时间窗内**最多执行一次**，连续事件期间也保证按固定节奏执行。**"按固定频率做"**。适用：scroll/drag/mousemove、API 限流、游戏循环输入、**按钮防重复点击**。
- **Leading / Trailing edge**：leading 首次立即执行（按钮要的就是这个手感），trailing 在窗口末尾补一次。
- **rAF 替代**：纯视觉更新优先 `requestAnimationFrame` 而非 setTimeout 节流。

来源（观点一致，取三处）：
- <https://www.jsguide.dev/topic/javascript-debounce-throttle>
- <http://uxpatterns.dev/glossary/t/throttle-debounce>
- <https://stackpractices.com/recipes/debounce-throttle>

**关键区分（本项目最容易搞混的一点）【判断】**：

> **Debounce 在这里是错的选择。** Debounce 的语义是"等用户停下来"，用在"点击播放语音"上会导致：用户连点 3 次 → 只在最后一次之后播一次 → 前两次点击在 300ms 内被吞掉且**毫无反馈**。这恰恰是当前 bug 的主观感受之一。
> **按钮/触发型交互应使用 leading-edge throttle**（第一次立刻响应，窗口内的后续调用丢弃），并在丢弃时**给出反馈**。

**Cooldown（冷却）与两者的区别【判断】**：前两者是"**事件频率**"维度的限流（跟用户点得多快有关），冷却是"**资源/内容**"维度的限流（跟上一次业务动作完成后过了多久有关）。三者**不是替代关系，而是叠加关系**：

```
用户点击
  │
  ├─[1] 硬节流 throttle(150ms, leading)  → 吸收物理抖动/误触，丢弃不反馈
  │
  ├─[2] 状态判断：当前是否 PLAYING？
  │       └─ 是 → 是否超过 grace period(500ms)？
  │                 ├─ 否 → 忽略（防"机关枪"），走反馈
  │                 └─ 是 → 打断并播新片段
  │
  ├─[3] 冷却：距上次结束 > cooldown(1500ms)？
  │       └─ 否 → 不播音频，但走"冷却中"反馈
  │
  └─[4] 内容去重：洗牌袋取下一片段（一轮内不重复）
```

### 3.2 时间参数的行业经验值

**A. 交互响应阈值（用于确定"何时必须给反馈"）**

| 阈值 | 含义 | 来源 |
|---|---|---|
| **0.1s / 100ms** | 「Limit for users feeling that they are directly manipulating objects in the UI」（直接操纵感上限） | 【业界/权威】Nielsen Norman Group，<https://nngroup.com/articles/response-times-3-important-limits> |
| **1s** | 「Limit for users feeling that they are freely navigating … without having to unduly wait」；**超过 1s 必须给用户"计算机正在工作"的指示** | 同上 |
| **10s** | 「Limit for users keeping their attention on the task」，超过需进度指示 + 可中断入口 | 同上 |
| **100ms** | 「A delay below roughly 100 ms for a discrete interaction, like tapping a button, will usually feel **instant**」 | 【厂商】Apple WWDC23《Analyze hangs with Instruments》，<https://developer.apple.com/videos/play/wwdc2023/10248/> |
| **250ms** | 「250 ms doesn't feel instant anymore… the delay is definitely noticeable」；工具默认从 250ms 开始报 hang | 同上 |
| **500ms** | 「Everything above 500 ms we consider a proper **hang**」；请求-响应式交互在 500ms 内不给额外反馈是可接受的 | 同上 |
| **44×44 pt** | 按钮最小可点击区域 | 【厂商】Apple HIG，<https://developer.apple.com/design/human-interface-guidelines/buttons> |

> Nielsen 原文特别强调这些阈值「have been the same for 46 years」「caused by the human brain's structure and are thus firm and stable decade by decade」—— 这是**最可靠的一组数字**，应作为本项目的取值基准。

Apple WWDC23 还有一段极贴切的论述（原文）：

> 「We treat the button as a "real" thing and we expect it to update in "real" time, instantly. So for the actual UI elements in our interface, we usually want to aim for this "instant" update.」
> 「If you have a request-response style interaction, 500 ms without any additional feedback might be OK.」

**这是"点击必须 100ms 内给视觉反馈、音频可以晚点到（最多 500ms 无额外反馈）"的直接依据。**

**B. 语音打断（barge-in）的行业参数默认值**

【业界】可检索到的配置默认值（两家独立来源，量级一致）：

| 参数 | 含义 | Sensitive / Balanced / Patient | 另一来源默认值 |
|---|---|---|---|
| Debounce | 两次打断之间的最小间隔，防"机关枪"式 stop-start | 250 / 500 / 750 ms | 100 ms（Client User Speaking Debounce） |
| Grace | 开始播放后多久才接受打断 | 200 / 400 / 600 ms | `lockout_seconds: 1.0`（另有 "Assistant Playback Grace Period" **1000 ms**） |
| Cooldown | 打断触发后检测器静默多久 | 500 / 1000 / 1500 ms | "Assistant Post Interrupt Backoff" 0 ms（可配） |
| Confirmation frames | 连续多少帧确认才认定打断 | 3 / 5 / 7 | "Barge-In Speech Start Duration" **0.45 s** |
| Soft hold / Quiet tail | 软打断判定窗口 | — | Probe timeout 600 ms / Post Quiet Tail 2000 ms |

来源：
- <https://swiftcase.co.uk/2026/07/07/voice-reliability-the-settings-you-change-after-go-live>（明确解释："Grace is how long after the agent starts speaking before it will accept an interruption at all… **Cooldown is how long the energy detector sits down after firing**"）
- <https://docs.intellibuddies.com/docs/conversational_agents/barge-in-configuration>
- <https://sdk.airefinery.accenture.com/tutorial/realtime/tutorial_realtime_bargein>（VAD 默认 `lockout_seconds: 1.0`、`grace_period_seconds: 3.0`）
- 语音识别防抖经验值 1200ms（多子句语种实测）：<https://os.maria-code.ai/blog/sentence-level-streaming-vui-architecture>

**C. 游戏 / 看板娘类产品的实际做法**

【业界】可查证的公开实现：

- **Live2D 看板娘（galnetwen/Live2D 等主流 hexo 插件系）**：点击/悬停 → `showMessage(text, timeout)`，**消息默认 3000ms 后淡出**；同一 showMessage 会**直接覆盖上一条**（即"打断"语义，非排队）。复制/控制台等事件 5000ms。参考 <https://deepwiki.com/galnetwen/Live2D/3.2-interactive-message-system>
- **Unity + Live2D Cubism 官方 SDK 路线**：点击模型 → 射线命中 → `_AudioSource.clip = _AudioClips[R]; _AudioSource.Play();` **直接覆盖当前 AudioSource**（打断）。文本气泡 8s 后隐藏。参考 <http://programmersought.com/article/38838260678/>
- **社区 Live2D Widget 交互范式**：`startMotion(name, no, priority)`，动作组名 `tap_body` / `idle` / `greet`，**带优先级参数**——高优先级动作可覆盖低优先级（等价于"重要语音可打断氛围语音"）。参考 <https://blog.csdn.net/gitblog_00726/article/details/153556087>
- **Web 宠物 / 对话气泡类实现**：点击生成带唯一 id 的气泡，`setTimeout(DURATION=1800ms)` 后按 id 移除；**多个气泡可并存**（即"排队/叠加"语义，用于纯文字气泡而非语音）。参考 <https://www.codedex.io/community/monthly-challenge/submission/5o5VozfORg5cNKQiXF3Z>

**结论【判断】**：**"打断"是角色语音类交互的绝对主流**（Unity/Live2D/看板娘全部是覆盖式播放）；纯文字气泡才会用"叠加/排队"。没有检索到任何主流角色语音产品采用"排队"。

### 3.3 W3C / HIG 对"重复触发同一反馈"的直接规定

**诚实结论：没有。**

【标准检索结果】WCAG / WAI-ARIA / WHATWG HTML / Apple HIG 中，**没有**针对"重复点击触发同一反馈"的具体时间参数规定。相关规定只存在于两个层面：

1. **激活状态的定义**（§1.4）：WHATWG 定义了 sticky / transient activation，其中 transient activation duration「expected be at most a few seconds」。这是唯一与"多快算连击"沾边的标准表述，且**只约束浏览器 API 门控，不约束页面自身的 UI 逻辑**。
2. ** WCAG 2.5 系列**（Target Size、Dragging Movements、Motion Actuation）约束的是"可点击性/可操作性"，不涉及重复触发。

**因此【判断】：所有时间参数都是"依据人类感知阈值（Nielsen / Apple）+ 行业默认值（barge-in 预设）+ 本项目素材实测数据"推导出来的，而非标准规定。报告中所有数值都标注了推导链，工程师若测试后觉得手感不对，可以调——但调的时候请回到这条推导链，而不是拍脑袋。**

## 4. 无障碍（Accessibility）规范

### 4.1 WCAG 1.4.2 Audio Control（Level A）—— 与本项目直接相关

【标准】WCAG 2.1/2.2 SC 1.4.2 原文：

> 「If any audio on a web page **plays automatically for more than 3 seconds**, either a mechanism is available to **pause or stop** the audio, or a mechanism is available to **control audio volume independently from the overall system volume level**。」

来源：<https://www.w3.org/WAI/WCAG21/Understanding/audio-control>

**关键条款（原文意图）**：

- 「In the context of this success criterion, "plays automatically" broadly refers to audio that is **not started/played as a direct result of a user's intentional activation**. For example, selecting a link or button with clear labelling or context that it will start an experience where audio will play is an example of starting **in response to a user's intended action**.」
  → **本项目点击触发的语音，属于"用户有意的激活"，不落入 1.4.2 的"自动播放"范畴**。
- 但 W3C 同时列出 **F93** 失败案例：「Failure of Success Criterion 1.4.2 for **absence of a way to pause or stop an HTML5 media element that autoplays**」。
- 相关充分技术：**G60**（3 秒内自动停止）、**G170**（在页面靠前位置提供关闭音频的控件）、**G171**（仅在用户请求时播放声音）。来源：<https://www.w3.org/WAI/WCAG21/Understanding/audio-control>（"Sufficient Techniques" / "Failures" 章节）

**对本项目的判定与建议【判断】**：

1. **合规层面**：点击触发 → 不是 "plays automatically" → **不强制要求停止控件**。但注意 **battle 槽最长 62.6s**：一旦用户点击触发，接下来一分钟无法停止，虽然不违规，体验与"可被随时打断"的精神相悖。**建议**：提供"停止当前语音"入口（再次点击 / Esc / 静音按钮），这同时也是 0.2 节"问题 B"的解药之一。
2. **强烈不建议**做「进入页面自动播 `enter` 槽」的"惊喜"设计：W3C 原文明说「we **discourage** the practice of automatically starting sounds (especially if they last more than 3 seconds), and encourage that the sound be started by an action initiated by the user」。
3. **字幕是加分项而非可选项的替代**：本项目已有双语字幕（`pet-subtitle.js`），对应 WCAG 1.2 系列（预录音频需要 transcript）。虽然点击语音属于"用户激活的短反馈"，但有字幕本身就是对听障/噪声环境用户的最佳支持，应保持。

### 4.2 状态播报：aria-live / aria-busy / role=status

【标准/厂商】MDN ARIA Live Regions：

- `aria-live` 取值 `off` / `polite` / `assertive`，**默认 `off`**；
- 「Normally, only `aria-live="polite"` is used. Any region which receives updates that are important for the user to receive, but not so rapid as to be annoying, should receive this attribute.」；
- 「`aria-live="assertive"` should only be used for time-sensitive/critical notifications… **it can be extremely annoying and disruptive and should only be used sparingly**」；
- 隐含 live region 语义的 role：`log`、`status`、`alert`、`progressbar`、`marquee`、`timer`；MDN 建议「add a redundant `aria-live="polite"` when using this role」以提升兼容性；
- **必须"先有空的 live region，再改内容"**：「Start with an empty live region, then – in a separate step – change the content inside the region.」
- `aria-atomic="true"` 让屏幕阅读器每次朗读整个区域（默认 `false`，只读增量）。
- `role="alert"` + `aria-live` 同时写在 iOS VoiceOver 上会**重复朗读**。

来源：
- <https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Guides/Live_regions>
- `aria-busy`：<https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Attributes/aria-busy>

`aria-busy` 语义【厂商】：「global ARIA state that indicates whether an element is currently being modified… set `aria-busy="true"` until loading is complete. Then set to `aria-busy="false"`. This prevents assistive technologies from announcing changes before updates are done.」

**本项目落地建议【判断】**：

| 元素 | 做法 | 依据 |
|---|---|---|
| 字幕容器 | **已经有内容**，加 `role="status"` + `aria-live="polite"` + `aria-atomic="true"` | 字幕是"更新中的状态"，polite 不打断；atomic 保证整句朗读而非增量 |
| 语音触发按钮（若新增实体按钮） | 状态变化时更新 `aria-label`（如"播放角色语音" / "正在播放…" / "稍后再试"） | MDN `play()` 官方示例就是这么做的：成功后把按钮文本与 `aria-label` 一起改为 "Pause"，失败改为 "Play" |
| 冷却/被拒提示 | 放进同一个 `role="status"` 区域，用 polite 播报"稍后再试" | 不要新建 `role="alert"`，避免打断 |
| **禁止** | 不要用 `aria-live="assertive"` 播报台词 | MDN 明确要求 sparingly |

来源（MDN `play()` 示例的 aria-label 做法）：<https://developer.mozilla.org/en-US/docs/Web/API/HTMLMediaElement/play>

### 4.3 按钮的 disabled / busy 状态如何暴露

【厂商】MDN `aria-disabled` 的完整说明：

- `aria-disabled="true"` **只做语义暴露**，不阻止功能、不改样式、不改变可聚焦性；
- HTML `disabled` 属性则会让元素**不可聚焦、不接收任何浏览事件、不参与表单提交**；
- 「there can be instances where elements need to be exposed as disabled, but are still available for users to find when navigating via the Tab key… **aria-disabled does not change the focusability**」
- 「Developers will still need to use JavaScript to fully disable the functionality of the element while also changing the appearance」
- 「If you are using CSS's `pointer-events: none;` to make an element non-clickable, **make sure you disable interactivity with JavaScript as well**. `pointer-events: none` prevents mouse clicks, but does not prevent the element from being activated via the keyboard.」

来源：<https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Attributes/aria-disabled>
（`disabled` 属性语义：<https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Attributes/disabled>）

**本项目的选择【判断】**：

> **用 `aria-disabled="true"` + JS 拦截 + `[aria-disabled="true"]` 样式，不要用 HTML `disabled`。**

理由：
1. 本项目的"禁用"是**短暂的**（冷却 1.5s、grace 500ms）。用 `disabled` 会让按钮**失去焦点**，键盘用户会被"踢出"焦点链，冷却结束后焦点无法自动回来——这是典型的可访问性反模式；
2. `aria-disabled` 保持按钮**在焦点链中、可读、可发现**，同时用 JS 拦截点击；
3. 样式需自己写（MDN 提示 `aria-disabled` 不提供 `:disabled` 用户代理样式），并注意对比度与 `forced-colors` 模式。

配套规则【判断】：
- 三态互斥：`idle` / `busy`（加载中，`aria-busy="true"`）/ `playing`；冷却期归入 `aria-disabled="true"` 而非 `busy`；
- **永远不要**用 `pointer-events: none` 代替 JS 拦截（MDN 明确警告键盘仍可激活）；
- 键盘可达性：若宠物/模型是 `<canvas>`，本身不可聚焦 → 必须另提供**真实的 `<button>`**（或用 `role="button" tabindex="0"` 的容器 + Enter/Space 处理）。Apple HIG 给出最小点击区 44×44pt。

## 5. 交互反馈设计（同类产品做法）

### 5.1 三种重复触发策略的对比与选型

| 策略 | 语义 | 优点 | 缺点 | 谁在用 |
|---|---|---|---|---|
| **打断（Interrupt）** | 立刻停掉当前、播新的 | 反馈即时，符合"直接操纵"；实现最简单 | 长句被切碎；连点会变成"机关枪" | **角色语音的主流做法**：Unity+Live2D 覆盖 AudioSource、看板娘覆盖气泡、语音助手 barge-in |
| **排队（Queue）** | 播完当前再播下一个 | 不丢内容 | **反馈与操作脱节**（第 2 次点击的声音可能 5s 后才响，用户早已遗忘因果）；队列无限增长 | 纯文字气泡/Toast 常见；语音场景少用 |
| **无视（Ignore）** | 播放中丢弃新请求 | 实现最简单 | **用户以为程序坏了** —— 这正是当前 bug 的主观体验 | 应仅用于"氛围型"低优先级反馈，且必须配视觉反馈 |

来源见 §3.2-C（Unity/Live2D/看板娘均为覆盖式）；语音助手 barge-in 见 §3.2-B。

**本项目选型：打断（interrupt with grace）+ 分层例外**【判断】

主论据：
1. **Apple 官方准则**：用户把 UI 元素当作"真实物体"，期待即时反应；WWDC23 明确 100ms 以上就不再"即时"，500ms 以上算 hang。无视策略直接违反这条。
2. **Nielsen 0.1s / 1s 阈值**：排队会让第 N 次点击的反馈延迟远超 1s，用户失去"直接操纵"感。
3. **行业事实**：所有可查证的角色语音实现（Unity/Live2D/看板娘/语音助手）都是打断式。
4. **本项目的具体伤害**：现有 25s 冷却本质上就是"无视"策略，用户已经明确抱怨了。

**分层例外（按槽位语义分派，推荐但非必需）**【判断】

| 槽位 | 中位/最长 | 策略 | 理由 |
|---|---|---|---|
| `click` | 5.2s / 6.2s | **打断**，grace 500ms | 用户主动点击，最强即时性诉求 |
| `happy` / `sad` / `surprise` | ~6s / 12.3s | **打断**，grace 800ms | 情绪句，稍长，给多一点保护 |
| `idle` / `sleep` | ~7s / 12.3s | **无视**，但必须有视觉反馈 | 氛围型，被系统自动调度，用户不期待即时响应 |
| `intel` | 4.4s / 7.3s | **打断**，grace 500ms | 信息句，短 |
| **`battle`** | **37.2s / 62.6s** | **无视 + 强制提供停止入口** | 62s 的音频绝不能被另一次点击"打断成碎片"，但必须能停 |
| `enter` | 9.6s | **打断**，grace 1000ms | 初见句，用户不会连点 |

> 若工程师想先做最小改动：**只实现 `click` 槽的打断 + 全局 grace 500ms**，其余槽位保持现状的"播放中无视"即可解决 90% 的抱怨。分层是 P1。

### 5.2 加载态 / 播放态 / 禁用态的视觉反馈惯例

【厂商 + 业界】汇总：

- **必须有 press state**：Apple HIG 原文「**Always include a press state for a custom button.** Without a press state, a button can feel unresponsive, making people wonder if it's accepting their input.」—— <https://developer.apple.com/design/human-interface-guidelines/buttons>
- **Loading 态**：Nielsen「For delays of more than 1 second, indicate to the user that the computer is working on the problem」；Apple「everything above 500 ms we consider a proper hang」（即 500ms 后必须有额外反馈）。→ **本项目音频加载若超过 500ms，必须出现 loading 指示**。
- **三态切换惯例**【业界】：`idle → loading(spinner/skeleton, aria-busy=true) → playing(进度/波形/波纹) → idle`；禁用/冷却态用**降饱和度 + 保留可读性**（不要降到对比度不达标，MDN 对 `aria-disabled` 的样式提示）。
- **纯视觉动画**用 rAF 而非 setTimeout 节流（见 §3.1）。

**本项目建议的三态视觉映射【判断】**

| 状态 | 触发 | 宠物/model 侧 | 按钮/字幕侧 | ARIA |
|---|---|---|---|---|
| `idle` | 默认 | 常态动画 | 按钮可点 | `aria-disabled="false"`, `aria-busy="false"` |
| `loading` | 点击后 `play()` 未 resolve，>500ms | 轻微"张口/蓄力"前摇 | 按钮转圈 / 字幕条出现骨架 | `aria-busy="true"` |
| `playing` | `playing` 事件 | 口型/呼吸同步、点击态高亮 | 按钮切"停止"、字幕淡入、可选波纹 | `aria-busy="false"`，`aria-label="停止语音"` |
| `cooling` | 冷却/去重命中 | **必做**：短促的"敷衍"微动作或摇头/摆手 | 按钮降饱和 + 工具条提示"稍等一下" | `aria-disabled="true"`，status 区播报"稍后再试" |
| `blocked` | `play()` 被拒 | 无 | 提示"点击页面任意处开启声音" | `aria-disabled="false"`，status 区播报 |

> **最重要的一条【判断】**：**"冷却中"必须能被用户看出来。** 现有代码冷却命中时完全静默，这是用户抱怨的直接来源。哪怕只是一个 200ms 的"摇头"微动作 + 字幕条闪一下"…"，都比毫无反应强得多。这一条的成本远低于调参，建议优先做。

## 7. 针对本项目痛点的推荐交互策略（可编码规格）

### 7.1 决策摘要

| 问题 | 决策 |
|---|---|
| 排队 / 打断 / 无视，选哪个？ | **打断（interrupt with grace）** 为默认；`idle`/`sleep` 用无视（配反馈）；`battle` 用无视 + 强制停止入口 |
| 冷却值？ | 同槽位 **1500ms**（从结束或被打断起算，二者统一）；全局 click 兜底 8s（P2） |
| 硬节流值？ | **150ms** leading-edge |
| 打断保护期？ | click/intel **500ms**；happy/sad/surprise **800ms**；enter **1000ms** |
| 内容去重靠什么？ | **洗牌袋**（一轮内不重复），不是时间冷却 |
| 冷却期反馈？ | **必须有**——微动作 + 字幕/按钮状态 + `aria-disabled` + polite 播报 |
| 实例管理？ | **单 `<audio>` 复用 + 切 src**，不用 `new Audio()`，不上 Web Audio 全量预解码 |
| 防假死？ | 五出口终态收敛 + **`dur*1000+2000ms` 看门狗** |

### 7.2 参考状态机（伪代码，可直接翻译）

```js
// ── 常量（取值推导见 §6.4，每行的依据都写在注释里）──
const HARD_THROTTLE_MS   = 150;    // Apple 100ms(瞬时)↔250ms(可感知) 之间靠下
const GRACE_MS           = { click: 500, intel: 500, happy: 800, sad: 800,
                             surprise: 800, enter: 1000, idle: Infinity,
                             sleep: Infinity, battle: Infinity };
const COOLDOWN_MS        = 1500;   // 语音助手 Cooldown 预设上沿
const WATCHDOG_PAD_MS    = 2000;   // 看门狗余量
const LOADING_HINT_MS    = 500;    // Apple: >500ms 算 hang，必须给反馈

// ── 状态 ──
// 'idle' | 'loading' | 'playing' | 'cooling'
let state = 'idle';
let audio = null;            // 单例
let watchdogId = null, loadingHintId = null;
let lastEventAt = 0;         // 硬节流用
let lastFinishedAt = {};     // slot -> ts（结束或被中断都写）
let startedAt = 0;           // 本段起播时刻，用于 grace
let currentSlot = null, currentClip = null;
const bag = {};              // slot -> 洗牌袋

function onUserTrigger(slot) {
  const now = Date.now();

  // [0] 首帧反馈：必须在 100ms 内，且必须同步执行（不等任何异步）
  playPressFeedback(slot);              // 按压态/微动作——Apple HIG 要求 press state

  // [1] 硬节流：吸收物理抖动，丢弃且不反馈
  if (now - lastEventAt < HARD_THROTTLE_MS) return REJECT.THROTTLED;
  lastEventAt = now;

  // [2] 播放中 → 打断判定
  if (state === 'playing' || state === 'loading') {
    const grace = GRACE_MS[slot] ?? 500;
    if (now - startedAt < grace) { feedbackCooling(slot); return REJECT.GRACE; }
    if (grace === Infinity)      { feedbackCooling(slot); return REJECT.NOT_INTERRUPTIBLE; }
    stopPlaying('interrupt');            // 打断：pause + 清 src + 写 lastFinishedAt
  }

  // [3] 冷却
  if (now - (lastFinishedAt[slot] || 0) < COOLDOWN_MS) {
    feedbackCooling(slot);               // ★ 关键：不播音频，但一定要有反馈
    return REJECT.COOLDOWN;
  }

  // [4] 取片段（洗牌袋去重）
  const clip = takeFromBag(slot);
  if (!clip) { feedbackCooling(slot); return REJECT.EMPTY; }

  return startPlay(clip, slot);
}

function startPlay(clip, slot) {
  setState('loading');
  currentClip = clip; currentSlot = slot; startedAt = Date.now();

  audio.src = clip.file;                // 复用实例；切 src 会中断上一次 play() → AbortError 需静默忽略
  audio.volume = 0.9;

  // loading 提示：Apple 500ms 阈值
  loadingHintId = setTimeout(() => { if (state === 'loading') showLoadingHint(); },
                             LOADING_HINT_MS);

  // 看门狗：ended 不能假设一定会来
  watchdogId = setTimeout(() => finish('watchdog'), clip.dur * 1000 + WATCHDOG_PAD_MS);

  const p = audio.play();               // ★ 必须在同步作用域内调用（Safari WebKit Bug 259925）
  if (p && p.catch) p.catch((e) => {
    if (e && e.name === 'AbortError') return;      // 主动打断，静默忽略
    if (e && e.name === 'NotAllowedError') { finish('blocked'); showUnmuteHint(); }
    else finish('error');
  });

  emit('voice-line', { clip, slot, subtitle: clip.subtitle });   // 字幕先行（不等 playing）
  return ACCEPT;
}

audio.addEventListener('playing', () => {          // 真正出声 → 才切 playing 态
  clearTimeout(loadingHintId); hideLoadingHint();
  setState('playing');
  emit('voice-playing', { clip: currentClip, slot: currentSlot });
});

audio.addEventListener('ended',   () => finish('ended'));
audio.addEventListener('error',   () => finish('error'));

/** 唯一的终态收敛出口：ended / error / blocked / watchdog / stop 全部走这里 */
function finish(reason) {
  clearTimeout(watchdogId); clearTimeout(loadingHintId);
  hideLoadingHint();
  if (currentSlot) lastFinishedAt[currentSlot] = Date.now();   // 统一：结束与被打断都写
  const slot = currentSlot, clip = currentClip;
  currentSlot = null; currentClip = null;                      // ★ 无条件清除，防永久锁死
  setState('idle');
  emit(reason === 'ended' ? 'voice-ended' : 'voice-stopped', { clip, slot, reason });
}

function stopPlaying(reason) {
  try { audio.pause(); } catch (_) {}
  audio.removeAttribute('src'); audio.load();                  // 释放已下载缓冲
  finish(reason);
}
```

### 7.3 三个"必须先做"的最小改动

如果工期紧，按这个顺序做，成本从低到高：

1. **【10 分钟】把 `SLOT_COOLDOWN_MS` 从 25s 降到 1.5s，并让冷却命中时发一个事件**（`pet:voice-cooling`），由字幕/按钮层显示"…"或短促微动作。这一条就能解决用户抱怨的绝大部分。
2. **【半小时】加看门狗 + 五出口终态收敛**。修掉"audio 引用残留 → 非 click 槽位永久静默"这个定时炸弹。
3. **【半天】改单实例复用 + 洗牌袋去重 + 分层 grace**。彻底解决 Safari per-element 许可、实例堆积、click 槽只有 5 段的重复问题。

## 8. 争议与取舍

### 8.1 争议一：冷却到底要不要？要 1.5s 还是 25s？

- **支持长冷却（现状 25s）的考虑**：防止连点刷屏、防止同一句反复出现、防止音频重叠。
- **反对**：25s 是**用"静音"实现"去重"**，代价是 30s 的零反馈窗口，直接违反 Apple「500ms 以上算 hang」与 Nielsen「0.1s 直接操纵感」。而且 25s 对"去重"这个目标来说**既不必要也不充分**——必要的是洗牌袋，25s 只是碰巧降低了重复概率。
- **取舍**：**保留"限流"这个目标，换掉实现手段**。冷却从 25s → 1.5s（防"机关枪"，对齐 barge-in 行业上沿 1500ms），去重交给洗牌袋（一轮内不重复，数学上保证）。【判断】

### 8.2 争议二：Grace period 取 500ms 还是 1000ms？

- 语音助手行业有两组默认值：**1000ms**（Intellibuddies "Assistant Playback Grace Period"、Accenture `lockout_seconds: 1.0`）与 **200/400/600ms**（SwiftCase 三档预设）。
- 差异来源：语音助手的 grace 是为了**防回声误判**（VAD 把 TTS 自己的声音当成人声），误判代价是"助手莫名其妙停下"。本项目是**显式鼠标点击**，不存在回声误判问题，grace 只需要防"手抖/误触"，代价低得多。
- **取舍**：click/intel 取 **500ms**（SwiftCase "Balanced" 400ms 与 "Patient" 600ms 之间），happy/sad/surprise 取 800ms（情绪句更长、更值得听完），enter 取 1000ms（对齐语音助手默认值）。**若实测发现连点把句子切得太碎，优先上调 grace 而非上调冷却**——因为 grace 只影响"打断的时机"，冷却会造成"完全无反馈"，前者伤害小得多。【判断】

### 8.3 争议三：单实例复用 vs 每次 `new Audio()`

- **支持 `new Audio()`**：实现简单；打断时直接丢弃旧实例，不会听到"咔哒"；天然并发（本项目的语音与 TTS 是两条独立链路，互不影响）。
- **支持复用**：**WebKit 官方明文要求**（"Change the source … instead of creating multiple media elements"）；**Safari 的自动播放许可是 per-element 的**，新建元素 = 重新判定许可，这是本项目在 Safari 上最可能翻车的点；内存 O(1)，不堆积已下载缓冲。
- **取舍**：**改复用**。但**只复用"角色原声"这一条链路**——`voice.js` 的 TTS 是动态 blob 内容，每次内容都不同，复用没有意义，且需要维护 `revokeObjectURL`，**保持现状的 `new Audio(blobUrl)` 是对的**（它已经正确处理了 URL 回收）。【判断 + 厂商依据】

### 8.4 争议四：要不要上 Web Audio？

- **支持**：零延迟起播、可精确调度、可叠加、可做可视化（口型同步）。
- **反对**：**内存算不过来**——双语音 755s，Float32 PCM @48kHz 约 145MB，@24kHz 约 72MB。对常驻的桌面宠物页面不可接受。且 MDN 明确 `AudioBuffer` 是「designed to hold **small** audio snippets, typically less than 45 seconds」。
- **取舍**：**不上全量**。仅可作为 P2 对 click 槽（中配 5 段 / 约 21s / 约 4MB PCM）做小池预解码。若将来要做口型同步（Lip-sync），届时再评估，且应改为"按当前槽位按需解码 + LRU 淘汰"而非全量。【判断 + 计算】

### 8.5 争议五：`aria-disabled` vs `disabled` 属性

- 两者的官方语义差异明确（MDN）：`disabled` 会移除焦点链且屏蔽所有事件；`aria-disabled` 只做语义暴露。
- 本项目冷却仅 1.5s，**用 `disabled` 会把键盘用户的焦点踢走**，冷却结束后焦点丢失——这是明确的可访问性反模式。
- **取舍**：用 `aria-disabled="true"` + JS 拦截 + 自定义 `[aria-disabled="true"]` 样式。代价是要自己写样式与高对比度适配（MDN 已给出 `forced-colors` 片段）。【厂商依据 + 判断】

### 8.6 争议六：WCAG 1.4.2 是否强制要求"停止"控件？

- **严格解读**：1.4.2 的 "plays automatically" 被 W3C 明确定义为「audio that is not started/played as a direct result of a user's intentional activation」，本项目是点击触发，**不落入该条款**。
- **宽松解读**：battle 槽 62.6s 的音频一旦触发就无法停止，与条款精神（"让用户能关掉背景声"）相悖；且 W3C 列出了 F93「absence of a way to pause or stop an HTML5 media element」失败案例。
- **取舍**：**不主张为了满足 1.4.2 而加**（合规上不必要），**但主张为了体验而加**——停止入口（再点一次 / Esc / 静音按钮）的成本极低，且能顺带解决 battle 长语音的体验问题。另外，静音开关（`rp_pet_voice_muted`）**已经存在**，这是 G170 要求的"关闭控件"的等价物，应确保在 UI 上**可见可达**（不能只藏在 localStorage 里）。【判断】

### 8.7 已知的材料局限

- 未检索到 **W3C/WHATWG/WCAG/Apple HIG 中任何关于"重复触发同一反馈"的具体时间参数规定**。本报告所有时间值均由「人类感知阈值（Nielsen / Apple）+ 行业默认配置（barge-in）+ 本项目素材实测」推导，已在 §3.3 明确标注。
- 未检索到《崩坏3》《原神》等商业游戏**官方公开**的角色语音冷却参数（属未公开实现细节）。§5 的同类产品结论来自可查证的开源实现（Unity+Live2D、hexo 看板娘、社区 Live2D Widget）与语音助手行业配置。
- SwiftCase、Intellibuddies、Accenture AI Refinery 的 barge-in 参数是**厂商产品默认值**，不是标准，但三家量级一致（Grace 0.2–1s / Debounce 0.25–0.75s / Cooldown 0.5–1.5s），可作为经验锚点。
