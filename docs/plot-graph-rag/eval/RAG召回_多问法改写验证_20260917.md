# RAG 召回 · 多问法改写验证（2026-09-17）

> 需求：检索时先用模型把问题改写成多种问法，再多路召回。
> 结论：**方向有天花板、本地模型做不到、暂不落地**。
> 有效形态是「补出答案实体名」，不是「同义改写」；而补名需要懂作品的强模型，
> 当前 `.env` 里的 LLM key 是 `ollama` 占位符（长度 6），打 deepseek 直接 401。

---

## 1. 已搭好的验证链路（两个脚本，均未改检索代码）

| 脚本 | 作用 |
|---|---|
| `scripts/diag_query_rewrite.py` | 调 LLM 生成 N 种改写 → 批量嵌入 → 量**候选池层面**的语义 recall@20 |
| `scripts/ab_query_rewrite.py` | 用改写（或 `--oracle-names` 上界）**端到端**跑主评测口径 strict / inject |

两者都支持：超时 + 失败降级为原查询、改写结果落盘复用（不重复烧 token）、
嵌入走批量接口（实测 4 条 466ms vs 串行 1345ms）。

## 2. 实测结果（新题集 multi-hop 40 题，两档配对）

| 档位 | 语义 recall@20 | strict | inject | 单次延迟 |
|---|---|---|---|---|
| 基线（无改写） | 57.5%（23/40） | 18/40 | 18/40 | — |
| 本地 qwen2.5:7b 改写 ×3 | 65.0%（26/40）**+3** | **18（Δ0）** | **15（Δ−3）** | **1957 ms** |
| 「完美补名」上界（用 ref 的答案名） | — | **23（Δ+5）** | 18（Δ0） | 仅多几次嵌入 |

负样本在全部档位均为 54 块 / 7 条失守 / 新增泄漏 2，**无变化**。

## 3. 三个必须知道的发现

### ① 本地 7b 只会同义改写，补不出实体名

```
原问：阿派朗岛上那位以数字命名的少女是谁？
改写：阿派朗岛上那位叫作数字的女孩是谁？ / 在阿派朗岛上，以数字为名的那位少女是谁？
```
三条改写都没补出答案 **37**。同义改写后语义向量几乎没变，所以：
候选池 recall 只 +3 题，端到端 strict 0、inject 反而 −3（改写占掉了语义通道的名额，
挤掉原本能覆盖证据的块——与之前"整体重排"翻车同源）。

### ② 真正有用的是「补实体名」，且上限明确

把题集 `ref` 里的标准答案名直接拼到查询尾部（= 模型 100% 补对时的上界）：
strict **18 → 23（+5 题，multi-hop 45% → 57.5%）**。
这是这条路线的天花板——**即使完美也只能拿 +5**，且 **inject 不涨**（产品真实口径）。

### ③ 强模型目前不可用

```
llm_provider=deepseek｜llm_base_url=https://api.deepseek.com/v1
llm_api_key 长度 6 → 实际值是 "ollama" 占位符
调用返回：401 {"message":"Authentication Fails, Your api key: ****lama is invalid"}
```
本机 ollama 有 `qwen2.5:7b` / `qwen2.5:1.5b` / `bge-m3` / `nomic-embed-text`，可用但不懂作品设定。

## 4. 处置：暂不落地到生产检索路径

理由（不是"没做完"，是数据不支持）：
- 当前唯一可用模型下端到端 **strict 0、inject −3**；
- 每次改写 **+1957 ms**，而检索 p50 才 714 ms——在线同步调用不可接受；
- 上界也只有 +5/40（multi-hop），且 inject 不涨。

### 要让这条路成立，两个前置条件

1. **填入有效的 LLM key**（`.env` 的 `ROLEPLAY_LLM_API_KEY`，现为 `ollama` 占位）；
2. **把 LLM 挪到离线**：用强模型批量预生成「问法 → 应补的实体名」映射，
   在线走项目已有的 `StaticMapIdentifier`（`EntityExpander` 的静态映射后端）查表——
   **在线零延迟**，且绕开"每次检索都调模型"这个死结。

前置满足后的复验命令（脚本已就绪）：

```
# 1) 离线批量生成改写/补名（落盘为缓存 JSON）
.venv/Scripts/python.exe -X utf8 scripts/diag_query_rewrite.py \
    --types multi-hop --variants 3 \
    --out data/knowledge/_audit/diag_qr_deepseek.json

# 2) 端到端复验（主评测口径）
.venv/Scripts/python.exe -X utf8 scripts/ab_query_rewrite.py \
    --types multi-hop \
    --rewrites data/knowledge/_audit/diag_qr_deepseek_rewrites.json \
    --out data/knowledge/_audit/ab_qr_deepseek.json
```

判据：`Δstrict > 0` 且 `Δinject ≥ 0` 且负样本失守条数不增——三条同时满足才值得落地。

## 5. 附带结论

- 语义通道的 top-5 名额是稀缺资源：任何"往里塞别的东西"的改动（整体重排、
  同义改写）都会挤掉原本能覆盖证据的块，表现为 **strict 不动、inject 下跌**。
  要扩召回只能**扩候选池后单独给名额**，不能替换原有名额。
- multi-hop 是两集一致的洼地（新题集 45%、300 题 50%），也是唯一能被"补名"
  明显改善的组（上界 +12.5pt）。
