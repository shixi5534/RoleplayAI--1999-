# T1 · bge-reranker 精排标定（2026-09-17，闸门判定：不达标，不落地）

## 实验设置

- 模型：`models/bge-reranker-base-onnx`（int8 ONNX，CPU 推理）
- 方式：spy `_fuse_channels` 取五通道并集候选池（cap k）→ CE 对 (query, chunk.text) 打分
  → top-8 包回 RetrievedChunk（分数映射回 [0.6, 1.0] 分带）→ 主评测口径
  （`scripts/ab_ce_rerank.py`，复用 `evaluate_case(chunks_transform=...)`）
- 基线复现：strict 195 / inject 177 / 负样本 54 块·7 条失守 / p95 497ms ✓

## k=30 结果（300 题）

| 指标 | 基线 | CE k=30 | 闸门 | 判定 |

## 判定：不落地

三个闸门两项未过，延迟闸门超一个数量级。按"闸门不达标不合入"规则，生产代码零改动。

## 原因分析

1. **延迟**：ONNX int8 在 CPU 上单对 ~100–170ms（实测 1520s/300题/k=30 → 每对 ≈ 170ms），
   不是冒烟时估的 20ms。CPU 路线无法满足 ≤100ms 增量。
2. **inject −3**：与"整体重排"同源的机理——CE 分数与"覆盖多组证据"不完全相关，
   精排后第 4–8 名被换成 CE 高分块，挤掉部分互补证据。
3. **strict +6**：说明精排确实捞回了一些正解块（质量信号是真的），
   但幅度不及补位重排（+12/+4），且代价高得多。

## 后续选项（供路线图更新）

- **GPU / TEI 服务化**：有 CUDA 设备时 CE 推理可降到 ~5–10ms/对，k=30 全程 ~150ms/题，
  延迟闸门可过——那时质量收益（+6）才值得重新评估。
- **与补位重排叠加**：CE 精排（+6）与补位 keep=5（+4）作用面不同（后者只在尾部补位），
  叠加是否互补需另测，但在延迟解决前无意义。
- k=20/50 未跑：k=30 已两项不达标，按闸门逻辑停止，避免继续烧 25 分钟/档。
