# T17 · 查询语言消融：中文 / 英文 / 拼接 / 双路融合（2026-09-17）

> 触发：用户提出"英语多那就转换成英语查"。实测结论——
> **纯英文替换会大幅倒退（−22）**，**拼接持平（−3）**，
> 而**中英双路融合是真改善（strict +7 / inject +8）**。
> 三种形态的差别，正是 CLIR（跨语言检索）里的经典分野。

---

## 一、四档实测（clean 300 题，同一判定口径）

| 档 | 形态 | strict | inject | 逐题变化 | 判定 |
|---|---|---|---|---|---|
| A | 基线：中文 query | **203** | **186** | — | — |
| B | **纯英文 query**（云端翻译） | **181（−22）** | **171（−15）** | 救 45 / 砸 70 | ❌ 大幅倒退 |
| C | 中英**拼接**（中文 + 英文） | 200（−3） | 187（+1） | 救 45 / 砸 70 | ⚠️ 持平（互相稀释） |
| **D** | **中英双路融合**（两路各自检索后合并） | **210（+7）** | **194（+8）** | **救 15 / 砸 8** | ✅ **真改善** |

四档负样本全部 **7/53 条、54 块**，无新增泄漏。

## 二、为什么"纯英文"反而更差（机理）

语料 89.5% 是英文——但**英文块是 ASR 转写**，中文块是**人工整理的正典文本**：

| | 英文块（8069，89.5%） | 中文块（887，9.8%） |
|---|---|---|
| 来源 | 英配视频 whisper 转写 | 灰机 wiki 正典 + 中配视频 |
| 专名拼写 | **不可靠**：`Eperon` vs 题面 `Apeiron`、`Xeno` vs `Zeno`、58.4% 块含 `?` 标记 | **准确**（人工校对） |
| 检索优势 | 覆盖面广 | 拼写可对齐 |

因此：
1. 中文 query 靠 bge-m3 的跨语言语义**同时**能打到英文块（不完美但可用）**和**中文正典块（拼写精确）；
2. 换成英文 query 后，**丢掉了中文正典这一路**，而英文块的拼写变体让关键词覆盖判定落空；
3. 拼接（C 档）则是把两种语义**混在一个向量里**，两边都不像——所以"救 45 / 砸 70"。
4. 双路融合（D 档）让两路**各自保留自己的优势**，只在结果层合并 → 救 15 / 砸 8，净 +7。

**一句话**：不是"用英文查"，而是"**中文路 + 英文路都要，且在结果层合而不是在查询层混**"。

## 三、与上午「实体扩展」的关系（重要）

| | 上午的实体扩展（已验证 +7pt） | 本次双路融合（+7 / +8） |
|---|---|---|
| 改什么 | **中文 query 上追加英文实体名**（top-3，白名单校验） | 语义通道**额外用英文 query 向量检索** |
| 影响通道 | 图谱通道 + 语义通道（query 文本变了） | **只影响语义通道**（图谱仍走中文） |
| 机制 | 用作品知识补出实体名 → 图路激活 | 用整句英文覆盖英配转写块 |
| 实测 | inject 186 → 207（+21 题，McNemar p<0.0001） | strict +7 / inject +8 |

**两者作用面不同，很可能可叠加**（一个补实体级、一个补句子级）——这是下一步最该做的实验。

## 四、生产落地形态（三种，按代价）

| 形态 | 延迟 | 说明 |
|---|---|---|
| **离线预生成**（推荐） | 0 | 对题集/高频问法离线翻译成英文并缓存（本次 300 条为云端生成，落盘 `en_queries_300_20260917.json`）；在线查表 → 双路检索 |
| **在线 LLM 翻译** | +1~2 s | 云端强模型翻译后双路检索；需超时（≤2s）+ 重试 + 失败降级为纯中文单路 |
| **不落地翻译，只扩实体名** | ~0 | 即上午的实体扩展路径（已验证 +7pt），效果略低但零延迟 |

**工程约束**：新增开关默认关；语义通道候选规模不变（只合并、不扩名额）；
失败/超时一律降级为中文单路（行为逐位不变）。
