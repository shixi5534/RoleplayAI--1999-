# RAG 召回 · 60 题 never_candidate 专项与「语义补位重排」（2026-09-17）

> 目标：解决失败 105 题里 **60 题正解块从未进入任何通道候选池**这一最大失分组。
> 结论：定位到「RRF 只按名次给分、深池块永远拿不到分」，采用**保留融合头部 + 余弦补位**
> 方案，全量 300 题 strict **195 → 207（+12）**，inject +1，负样本零恶化，已落地为
> **默认关闭**的生产开关并完成回归验证。

---

## 1. 定位：三层诊断

### 第一层：正解块到底在哪（60 题全库排名）

出处 `data/knowledge/_audit/diag_gold_rank_20260917.json`：

| 口径 | top-20 | top-50 | top-100 | top-500 | 全库 | 分位（best rank） |
|---|---|---|---|---|---|---|
| 语义向量全库 | 31.7% | 50.0% | 55.0% | 76.7% | **100%** | p50=54, p75=379, p90=1665 |
| BM25 词法全库 | 11.7% | 15.0% | 25.0% | 35.0% | 43.3% | p50=81 |

- **正解块 100% 在语义索引里**，只是排名靠后 → 不是"索引没这块"，是"排序拿不到"。
- 词法路 56.7% 的题**零命中**（一个 query 词都没打中）→ 结构性不可达，别指望它。
- **60/60 的正解块文本含真阳实体名**（含种子名的只有 36/60）→ mention 通道本该取到，
  说明卡在候选池截断或排序，而不是块里没有信号。

### 第二层：候选池截断是不是瓶颈

出处 `data/knowledge/_audit/ab_mention_depth_20260917.json`（生产 `mention_per_entity=5`、
`mention_total_cap=10`）：

| 档位 | gold 进入候选池 | 60 题 strict | 候选池均块数 |
|---|---|---|---|
| (5, 10) 生产 | 0 题 | 0 | 8.9 |
| (20, 50) 放大 | **19 题** | **1** | 42.0 |

**19 题 gold 进了池却只救回 1 题** → 瓶颈从「召回面」转到「排序」：
RRF 按名次给分，排在 20 名开外的块拿不到足以进预算的分数。

### 第三层：重排能不能捞上来

出处 `ab_rerank_ceiling_20260917.json` / `ab_rerank_all_20260917.json` 等（**全量 300 题**）：

| 档位 | strict | inject | 负样本失守 | 注入块数 |
|---|---|---|---|---|
| A 基线（生产） | 195 | 177 | 7/53 条 | 54 |
| B 只扩池 (20,50) | 194（−1） | 171（−6） | 7/53 | 54 |
| C 扩池 + **整体**余弦重排 | 196（+1） | **151（−26）** | 7/53 | 54 |
| D 扩池 + **补位**重排（keep=3） | 206（**+11**） | 178（+1） | 7/53 | 54 |
| E **不扩池** + 补位重排（keep=3） | **207（+12）** | 178（+1） | 7/53 | 54 |

两个必须记住的教训：

1. **整体重排是有害的**：余弦偏袒「与 query 整体最像」的块，选出的 8 块高度同质，
   丢掉 RRF 多路命中带来的**互补证据**；而 inject 口径（2400 字符装配）恰恰需要多块
   互补才能覆盖全部证据组 → strict 只 +1，inject 反而 −26。
2. **只看子集会误判**：补位重排在 60 题子集上救回 9 题，看起来是 +9 净收益；
   全量一跑才发现它同时砸掉了若干已通过的题，真实净收益是 +12（另一批题）。
   **收益判定一律用全量口径，子集口径只用来解释收益从哪来。**

## 2. 落地实现（默认关闭，零回归）

| 文件 | 改动 |
|---|---|
| `src/roleplay/config.py` | 新增 `plot_rerank_topup_enabled: bool = False`、`plot_rerank_topup_keep: int = 3`（含实测注释） |
| `src/roleplay/core/knowledge/plot_graph.py` | `PlotGraphRetriever.__init__` 接收两参数；新增 `_rerank_topup()` 与 `_semantic_hash2row()`；`retrieve()` 在 `_rescue_floor()` 之后按开关调用；`PlotGraphRegistry.__init__` 与 `get()` 透传 |
| `src/roleplay/core/knowledge/factory.py` | 从 Settings 读取并传入 |
| `tests/test_plotrag_p0.py` | 透传断言 + 新增 `test_rerank_topup_off_is_noop`（关闭时检索结果逐位一致） |

设计要点：

- **只补位、不重排**：保留融合结果前 `keep` 名（默认 3），剩余名额用候选池中查询余弦
  最高的块补齐。头部是 RRF 多路命中的互补证据，必须保住。
- **分数带对齐**：补位块分数线性映射到 `[FUSE_MIN_SCORE, 头部最低分 − ε]`，
  保证名次不被打乱（`persona_prompt` 的门依赖这个分带）。
- **复用已有查询向量**：`retrieve()` 里语义通道已嵌入一次，补位直接复用 `qvec`，
  不增加第二次嵌入开销。
- **numpy 惰性导入**：只在功能启用时才 import，默认关闭路径零依赖开销。
- **降级路径**：语义索引缺失 / 无 qvec / 无候选 → 原样返回 `fused`，行为逐位不变。

启用方式（部署侧在 `.env` 或环境变量）：

```
ROLEPLAY_PLOT_RERANK_TOPUP_ENABLED=true
ROLEPLAY_PLOT_RERANK_TOPUP_KEEP=3      # 可选，默认 3
```

## 4. 上线步骤与回滚

1. 先在目标环境跑一次全量基线：`scripts/eval_plot_rag.py --out <基线>.json`。
2. 开启开关后跑第二次，用 `--baseline <基线>.json` 让脚本自行判定回退（退出码 3 = 回退）。
3. 判据：strict 不降、inject 不降、**负样本失守条数与新增泄漏不增**、p95 增量 ≤ 100 ms。
4. 回滚：把 `ROLEPLAY_PLOT_RERANK_TOPUP_ENABLED` 置回 `false` 即可，
   代码路径为 no-op，无需改代码、无需重建索引。

## 5. 风险与边界

1. **换语料需重新标定**：`keep` 的最优值依赖块排名分布；本结论只在当前 9021 块语料
   （英文 ASR + 中文提问）上成立，换语料必须重跑全量消融。
2. **依赖语义索引**：语义通道降级（嵌入器回退 hashing）时补位自动失效，
   检索行为退回现状——不会变差，但也拿不到收益，需靠既有护栏 fail loud。
3. **gold 判定为启发式**（evidence 关键词 ∪ oracle full 块），诊断层数字有标注误差；
   但本方案的**收益数字来自主评测口径**，不依赖该启发式。
4. 未验证 cross-encoder 重排（B3）；本方案用的是已有查询/块向量的余弦，
   若日后接入 reranker，应重新比较「补位 + reranker」与现状。
