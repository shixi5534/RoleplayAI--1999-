# 大白话版：GraphRAG 计划到底出了什么问题，该怎么修

> 面向不懂技术细节时的解释。所有数字的来源都是我在你的真实数据上跑出来的，见 `graphrag-phase2-audit-20260909.md`。

---

## 一、先说这套东西在干什么

你的 AI 角色（无名者）回答问题时，需要去资料里"找答案"。现在有两条找路：

**老办法（向量检索）**——现在在用的
把 2085 段资料全部变成一串数字（向量），用户问一句话，就把这句话也变成数字，找最像的几段。

问题：**这个方法在你们的数据上基本失灵了**。项目自己的注释写着：相关段落的相似度是 0.702，无关段落是 0.695——两个数字几乎一样，等于区分不出来。所以才把"只取最像的 2 段"（`top_k=2`）当成降噪手段，说白了就是"反正分不清，那就少给点"。

**新办法（图谱）**——计划要做的
先从资料里抽出"谁 - 做了什么 - 谁"这样的关系，存成一张关系网。用户问问题时，先找到问题里提到的那个人/物，然后在这张网上顺着关系走两步，找到相关证据。

**这张网已经有一份**（剧情图谱，从视频字幕建的）：5026 个实体、4261 条关系。计划要做的，是给 lore（那 2085 段手工资料）再建一张类似的网。

---

## 二、核心问题：它把一个"开关"包装成了一个"大工程"

### 2.1 事情的原委

每条关系上会挂一个"凭证"（evidence），记录这条关系是从哪段资料里抽出来的。计划里有一条规则：

> 凭证少于 2 条的关系 = 孤证 = 不可靠 = 丢弃。

我数了一下你现有的 4261 条关系：**4248 条（99.7%）只有 1 条凭证。**

也就是说严格执行那条规则的话，**只有 13 条关系能用——这张网直接废掉**。

计划的 v6 版本发现了这个问题，给出的解法是：别丢了，改成"打折"——只有 1 条凭证的关系，权重乘以 0.35。然后还打算做一个参数扫描，从 `0.0 / 0.2 / 0.35 / 0.6 / 1.0` 里挑一个最好的。

为了这件事，计划专门新增了一个阶段 W、4 个配置项、一套五层测试体系、外加一批人工标注工时。

### 2.2 我实测的结果：这个旋钮基本不起作用

我把 5 个档位都在你的真实图谱上跑了一遍（40 个最热门的实体，每个做一次检索）：

```
factor=0.0    只用了 13 条边     结果与前 10 名重合度 21.5%
factor=0.2    用了 4261 条边     重合度 97.2%
factor=0.35   用了 4261 条边     重合度 98.2%
factor=0.6    用了 4261 条边     重合度 99.3%
factor=1.0    用了 4261 条边     重合度 100%（参照）
```

**除了"关"和"开"之外，中间那几个档位几乎没有区别（97%~99% 重合）。** 参数扫描跑完会得到一条基本平平的线，根本选不出"最好的那个值"。

### 2.3 为什么会这样？（一个比方）

PageRank 的流动规则是"按每个节点的总流出量归一化"。打个比方：

一个水池（实体）往外分水，接了几根水管（关系）。真正决定水往哪流的，**是每根水管占了多大份额**，而不是每根管子绝对多粗。

既然 99.7% 的管子都同时乘以 0.35，**份额完全没变，水流方向当然也就不变**。

### 2.4 那 99.7% 到底为什么只有 1 条凭证？

因为**每段资料都是单独抽取的**。同一个事实（比如"无名者认识维尔汀"）在你的资料里多半只被写过一次；就算写了第二次，措辞不同，抽出来的关系名字也不一样，变成了另一条独立的边。

我做了验证：**即使把同一对实体的所有不同关系名全部合并，"凭证 ≥2" 也只能从 0.31% 抬到 3.12%**。

**结论：这不是一个需要调参的阈值，这是一个从一开始就达不到的标准。** 想靠调 0.35 还是 0.6 来解决，方向就错了。

### 2.5 正确做法（一行配置，不是一整个阶段）

```
graph_include_weak = True        # 打开，别再丢单凭证的边
+ 展示时给这些边打个 0.5 折      # 剧情层已经是这么做的，直接照抄
+ 加一个"查不到东西"的计数器     # 用来观测这条路到底活着没有
```

**完事。** 省掉整个阶段 W、4 个配置项、10 组参数扫描、半个到一天半的人工。

## 三、真正该做的事：给关系的名字定规矩（这是提升数据质量的正解）

**回答你的问题：是的，核心就是提升数据质量——但抓手不是重新清洗语料，也不是换模型，而是"约束关系的名字"。**

### 3.1 现在有多乱

你现有的 4261 条关系，用了 **1564 个不同的关系名**，其中 **72%（1128 个）全世界只出现一次**。

正常的那批（还行）：
```
前往(346次)  持有(176)  象征(111)  隶属于(68)  背叛(65)  拥有(53)
```

乱的那批（直接从你图谱里拿的原样）：
```
不    不与   不会   一度繁荣   一手推动   下达   下达命令
不同于  不属于  不隶属于  不如其专业  不宜承担  不过是
不符合描述  行心力  用 RFID？
```

**根因**：抽取时只告诉模型"用简短中文谓语"，是个**开放填空**，没给它一张固定词表。模型就自由发挥了。

2026 年业界对 GraphRAG 的第一条共识就是这件事：

> "抽取之前必须先限定允许的关系词表。如果不约束，同一个意思会被抽成不同的词，把图谱撕成碎片，关系网根本连不起来。"
> —— GraphRAG Best Practices（kindatechnical）
>
> "不要跑一个通用的抽取流水线然后指望图谱有用。**如果你说不出你的边到底是什么意思，图谱就不会帮上推理的忙。**"
> —— When to Use KG-RAG（ML Digest）

### 3.2 为什么这事很严重（比听起来严重）

因为这条关系名会被直接拼成一行字，**塞进 AI 看到的提示词里**：

```
【关系脉络】
无名者 —前往→ 圣洛夫基金会          ← 正常
xxx —行心力→ yyy                    ← 这种话会真的被 AI 看到
xxx —用 RFID？→ yyy
```

**AI 在回答时，上下文里就是这么一行鬼话。** 它会污染回答质量。最阴的地方是：**图谱的统计数字看起来完全正常**（5000 多个实体、4000 多条边，一切良好），你从数字上根本发现不了。

而且计划要做的"打开单凭证边"，会让**这批垃圾关系从原来只有 13 条能用，变成全部都有机会进入提示词**——不先治理就打开，等于主动扩大污染面。

### 3.3 怎么修（半天到一天）

1. **定义一张受控词表，40~80 个词。**
   不用从零想，把现在的高频词收进来就行——仅前 30 个高频词就覆盖了大部分边。可以合并的：`前往/去往/抵达/来到` → `前往`；`属于/隶属/隶属于` → `隶属`。

2. **改抽取提示词**：明确告诉模型"只能用下面这些词，表外的先映射到最接近的，映射不了就别输出"。

3. **对已经建好的 4261 条边离线归一遍**（用小模型把 1564 个词合并到标准词），成本远低于重建。

4. **加卫生过滤**：谓语超过 8 个字 / 含标点 / 命中垃圾黑名单 → 直接丢弃。
   注意：这条规则计划里只给"对话边"写了，**lore 那一层完全没有**。

5. **写成验收标准**（现在完全没有，必须补）：
   - 唯一关系名 ≤ 300 个
   - 只出现一次的关系名占比 ≤ 40%
   - 黑名单命中数 = 0

## 四、另外四个必须处理的问题

### 4.1 打开之后，速度慢了 122 倍

```
只用 13 条边时：一次图谱检索 0.7 毫秒
打开 4261 条边：一次图谱检索 85.8 毫秒（而且 50 次迭代跑满都没算完）
```

顺便提醒：**你的剧情层现在已经是打开状态了**，也就是说**现在每轮对话已经在付这 86 毫秒**。

**修法**：先做一个快速的"两跳邻居"搜索找出小范围的子图，再只在这个小图里算 PageRank。2 跳以内的子图比 4261 条边小得多——又快、又能算完、还顺手消灭了计划里"两个函数口径必须一致"那个补丁。

### 4.2 评分系统是"自己给自己打分"

计划自己立了条红线：*"judge 模型不能用生成回答的那个模型，有自抬身价的偏差"*。

但实际代码（`scripts/eval_rag_standard.py` 第 708 行）写的是：

```python
JUDGE_MODEL = s.llm_model      # 也就是 qwen2.5:7b，正是生成答案的那个模型
```

**自己写答案，自己判分数。**

后果：**你现在看到的所有评分都可能是虚高的**。外部研究说同源 judge 会带来 10~25 个百分点的虚高（Zheng et al. 2024）。

**修法**：
- 给 judge 一个**独立的配置项**，允许指向别的模型（云端 GPT-4o-mini 级别，或另一个不同家族的本地模型）；
- 做 50~100 条人工判过的样本，算 judge 与人的一致率（Cohen's kappa），≥0.6 才允许用它下上线结论。

### 4.3 验收标准现在是"死锁"的

计划定了一条绝对门槛：**Faithfulness ≥ 0.80**。

我查了你们现成的评测数据（`deliverables/rag-eval-standard.json`，60 条用例）：

```
faithfulness 均值 = 0.712   （注意：脚本自己的门槛是 0.90）
```

**对照的那一组自己就没达标。** 而按计划自己的规则（"绝对门槛没过 = 判不通过"），那么无论图谱多有用，最后都只会判"不通过"——而把 0.712 提到 0.80，**计划里没有任何一步负责做这件事**。

还有 multi-hop（多跳问答）：只有 9 道题，其中 **5 道已经是满分**（没法再提升），剩下 4 道。理论上限只能提升 25.6%，计划要求提升 15%——意味着这 4 道必须几乎全部提到满分，**错一道就不达标**。这缺乏起码的可行性验算。

**修法（二选一）**：
- A：把绝对门槛改成"**不低于重新测出来的基线**"，先证明图谱确实有提升就行；
- B：单独开一个小任务，先把 faithfulness 从 0.712 拉过 0.80，再来做 A/B。

外加：multi-hop 的题目从 9 条扩到 ≥30 条，并且**重新分配难度**（现在这种一半满分的分布，根本测不出差别）。

### 4.4 你的知识库之前是"半瞎"的，而且你不知道

我跑测试的时候，系统打印了这么一串：

```
知识库命名空间 lore_wu_ming_zhe 的嵌入器已变化（保存=hashing/768，
  当前=ollama:nomic-embed-text/768），正在用当前嵌入器自动重建向量
```

翻译：**你的 lore 主知识库里存的不是真正的语义向量，而是一种应急兜底的假向量。**

推测经过：某次 Ollama 没起来 → 系统静默退化成应急模式 → 把这些应急向量写进了你的知识库文件 → **之后你一直在用一个半瞎的检索器，而系统一声不吭**。

我那次操作触发了自动重建，**现在已经修好了**（真实语义向量，2085 段一段没少，文字一条没丢，只是文件从 15.3MB 变成 24.7MB）。

**但坑没堵上，以后还会发生。更麻烦的是**：如果你在这两种状态之间做 A/B 对比，测出来的"图谱有提升"其实是"检索器恢复了"。这正好命中业界的那句警告——"很多所谓的 GraphRAG 胜利，其实是赢了那个很弱的基线"。

**修法**：加一条硬校验——启动时发现嵌入器身份和存档不一致，**直接报错退出，不要悄咪咪自动重建**；并且在每次评测报告的开头记录当次用的嵌入器身份。

### 4.5 还有一个前提：Git 仓库一次提交都没有

我查了一下，仓库现在是零提交状态：

```
git rev-list --all --count  →  0
```

这直接导致计划里所有"打 tag""探针集版本化""保留回滚 tag""11 条提交粒度建议"——**一条都执行不了**。

**修法**：先做第一次提交，10 分钟的事。

## 五、所以该怎么干：一个能直接照着执行的顺序

### 第 0 步（10 分钟）
Git 首次提交，把现在这个干净状态存下来。

### 第 1 步 · 数据质量（半天 ~ 一天）——**最重要，排在最前**
- 定义 40~80 个受控关系词
- 改抽取提示词，强制只能用这些词
- 对已有的 4261 条边离线归一遍
- 加谓语卫生过滤（>8 字 / 含标点 / 黑名单 → 丢）
- **把关系词卫生写成图谱验收标准**

### 第 2 步 · 三个小修补（半天）
- 修 `Event loop is closed` 这个抽取失败（我实测 2 段就失败 1 段；前一轮审计报告里就记着，到现在没修）
- PPR 改成"先取 2 跳子图再算"，把 86ms 压回去，并设明确的延迟上限
- judge 加独立配置项 + 建人工校准集

### 第 3 步 · 建 lore 图谱（机器 4~6 小时 + 人工半天）
- 用修好的抽取提示词跑全量 2139 段
- 补角色卡的别名表（现在那一栏是空的，这是真痛点，填对了收益最大）
- 验收加上第 1 步的关系词卫生标准 + 检索烟雾测试（10 条查询至少 6 条要有结果）

> 注意排期：计划写"机器 1~2.5 小时"偏乐观。按它自己的参数估算（并发 4、单段 20-30 秒），2139 段约 **3.7 小时**，再算上失败重试和人工巡检，**按 4~6 小时排**。

### 第 4 步 · 一行配置，代替整个阶段 W
```
graph_include_weak = True + 展示层 0.5 折 + 空结果计数器
```
省掉原计划的阶段 W、4 个配置项、10 组参数扫描、1~1.5 天人工。

### 第 5 步 · 查询改写 + 去重（1 天）
原计划的阶段 R。这部分写得很扎实（尤其"改写只喂检索、绝不替换用户原话"那条红线），照做。

### 第 6 步 · 评测
- **先在第 1 步修完后重新测一遍基线**（旧的 0.712 很可能是在坏数据上测的）
- 然后把门槛改成"不低于新基线"，或先单独修 faithfulness
- 探针集扩到 30 条以上

### 可以往后放或砍掉的
- 阶段 P3（社区摘要）：我测过，最大连通分量有 2441 个实体、占了全部连边实体的 73.4%，**"找社区"在这个图上会退化成一个巨型社区**，压成两三句话毫无意义。开工前必须先做可行性预检，不通过就降级成"按关系类型/时间线的话题索引"。
- 阶段 O 里的向量格式迁移：收益是真的（实测 49MB → 6MB），但要改持久化格式、牵连旧库兼容，**建议放到最后或者单独立项**。

## 六、一句话总结

**这份计划把一个"改一行开关"的事，包装成了一个需要参数扫描、五层测试和人工盲评的大工程**——而我实测证明了那个参数是平的，几乎不影响结果。

**同时它漏掉了三件真正决定成败的脏活**：
1. **给关系的名字定规矩**（1564 个词里 72% 只用了一次，而且已经进 AI 的提示词了）；
2. **防止知识库静默退化**（已经发生过一次，你之前一直在用半瞎的检索器）；
3. **别让 AI 自己给自己打分**（judge 就是被评的那个模型）。

**回答"提升数据质量还是什么"：是。核心就是数据质量，但抓手是"约束关系词表"，不是重洗语料也不是换嵌入模型。**
