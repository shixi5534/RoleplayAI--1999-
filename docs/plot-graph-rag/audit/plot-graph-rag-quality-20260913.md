## 1. 分诊：失败到底是数据问题还是算法问题

### 1.1 为什么必须做这个

上一轮报告的结论是「严格通过率 46.0%，与旧实现持平」——但**"没检索到"这句话背后
有六种完全不同的病因，修复动作、成本、风险都不一样**：

| 根因 | 含义 | 该做什么 |
|---|---|---|
| `corpus_gap` | 语料里没有任何块含该证据词 | 联网补资料 |
| `no_entity_gap` | 证据组的关键词在图谱里找不到对应实体 | 补实体 |
| `alias_bridge_gap` | 实体在图里，但**查询里根本没出现它的任何名字** | 补中文别名桥（数据） |
| `graph_gap` | 语料有块，但这些块一条都没被图谱引用为证据 | 重建图 |
| `link_bug` | 名字就在查询里却没链上 | 修链接 |
| `retrieval_gap` | 图谱记了证据、也够得着，但没取回 | 修排序 |

不分类就动手，等于把钱花在错的地方。

### 1.2 工具

`scripts/triage_plot_rag.py`：逐题判定每个缺失证据组的根因，产出五份行动清单
（语料缺口 / 实体缺失 / 别名桥缺失 / 建图缺口 / 检索缺口），落盘
`data/knowledge/_audit/plot_rag_triage_final.json`。

### 1.3 结果（本轮开始前，300 题 / 188 个缺失证据组）

| 根因 | 组数 | 占比 | 面 |
|---|---|---|---|
| **别名桥缺失** `alias_bridge_gap` | **147** | **78.2%** | 数据 |
| 实体缺失 `no_entity_gap` | 6 | 3.2% | 数据 |
| 建图缺口 `graph_gap` | 4 | 2.1% | 数据 |
| 语料缺口 `corpus_gap` | **0** | 0% | 数据 |
| 链接缺陷 `link_bug` | 11 | 5.9% | 算法 |
| 接不上 `unreachable_gap` | 4 | 2.1% | 算法 |
| 检索缺口 `retrieval_gap` | 16 | 8.5% | 算法 |

**数据面 157 / 188 = 83.5%｜算法面 31 / 188 = 16.5%**
（本轮结束时：**数据面 134/162 = 82.7%**——比例稳定，说明"修的正是数据面"。）

### 1.4 三个结构性事实（逐条实测）

1. **语料是英文 B 站 ASR**（7964/9021 块），**用户提问是中文**，图谱
   `fingerprint.embedder = "none"`——**没有任何跨语言兜底**；
2. 中文正名实体里**1820/2949（62%）的中文名在语料中零命中**，只有 47 个进了人工别名表；
3. 用户提问常常**只描述、不点名**（「海盗船上的歌手」「自囚的医生」「雾中女巫」），
   而检索是**实体链接驱动**的：链不上实体 ⇒ 整条路都断了。

典型例子：

```
Q: 洞穴的囚徒篇里海盗船上的歌手是谁？
   seed = ['洞穴', '海盗']          ← 链接到的是篇章词，不是答案
   答案 = 星锑 / Regulus            ← 图里有这个实体，但查询里没有它的名字
Q: 伦敦十字街的雾中女巫是谁？
   seed = ['十字街']                 ← 答案 薇洛/Willow 的称号「雾女士」不在别名表里
```

## 2. 以灰机为标准：抓取通道与正典库

### 2.1 灰机 wiki 直连被 Cloudflare 挡死

`requests` / `web_fetch` / playwright headless **一律 403「请稍候…」**（Ray ID 挑战页）。
实测可行的唯一路径：**真实 Chrome（`channel="chrome"`、非 headless、去自动化特征）
打开页面后等 25–35 秒**，挑战自行放行；此后在**页面上下文里**同源 `fetch` 打
MediaWiki API（Cookie 自动带上），拿到的是结构化 JSON 而非 HTML。

→ `scripts/huiji_fetch.py`（带磁盘缓存，幂等：命中即不联网，重复跑零成本）

### 2.2 正典库（`data/lore/wu_ming_zhe/huiji_canon.json`）

| 类别 | 数量 | 来源页 |
|---|---|---|
| 章节（篇 / 集）中英对照 | 54 | `章节列表/主线故事` |
| 可征集角色 中英名 | 141 | `Category:角色` + `displaytitle` |
| 其他角色（NPC）中英名 / 身份 | 184 | `其他角色一览/1.x·2.x·3.x` |
| **全站命名表**（displaytitle 扫描） | **576** | `list=allpages` 全量枚举 |
| 关键术语 / 组织 / 地点页原文 | 25 | 各专页 |

> 例：`洞穴的囚徒 = The Prisoner in the Cave`（1.4）、
> `今夜星光灿烂 = e lucevan le stelle`（1.7）、`孤独之歌 = Vereinsamt`（1.9）、
> `疯癫与文明 = Folie et Déraison`（2.6）、`卡穆塔 = Kamuta`、`塞洛尼 = Selone`。

**踩坑记录**：全站枚举第一版只拿到 616 页就停了——MediaWiki 的续传令牌在**响应根级**
的 `continue`，我误取 `query.continue`，于是枚举在第一页（500 条）就结束，而脚本仍报
"采集完成"（15 条中英对照）。修正后 155 次 API 调用拿到 **576 条**。
这类"静默少采"比崩溃更危险，已在代码里写明。

### 2.3 正典中文语料层（本轮最大的数据增量）

灰机 `小径/<篇名>` 是**官方中文剧情原文**——实测 **116 页 / 约 30 万汉字**。

→ `scripts/huiji_canon_corpus.py`：抓渲染文本 → 剥掉每页顶部「全部篇名导航 + 目录」块
（**必须剥**：不剥的话 40 多个篇名会在每一页里各命中一次，把词法检索彻底稀释；
判据只能用**段末句读标点**——用"含逗号就不算导航"会在「再见，来亚什基」处提前停下）
→ 落 `data/lore/wu_ming_zhe/canon_zh/<篇名>.md`（头部带来源 URL，逐块可溯源）。

→ `PlotCorpus.build()` 新增 `canon_zh/` 解析路径：`source_kind="canon_zh"`、
`doc_id="huiji_<篇名>"`、`source_type="plot_canon"`，与 B 站文档天然隔离。
**落库 112 篇 / 29.7 万字 / 663 块**（语料 8358 → 9021 块）。

### 2.4 别名桥治理

| 动作 | 内容 | 依据 |
|---|---|---|
| 灰机核实的新桥 | **47 条**（`Eternity→玛丽莲`、`天使娜娜→金伯利女郎`、`勿忘我先生→勿忘我`、`德鲁维斯→槲寄生`、`Lyra→歌唱家`、`suitcase→箱子`、`Kanjeera→坎吉拉`…） | 灰机命名表**中英名精确对照** |
| 自相冲突合并 | 13 组（`Ulrich↔乌尔里希`、`Aleph↔阿莱夫`、`Barcarola↔芭卡洛儿`、`金伯利女郎→天使娜娜`、`金蜜儿→布朗妮`…） | 同一个名字既做键又做别名 ⇒ 重建时**抢名字生成两个节点**，证据被劈成两半 |

别名表 198 → **227 条**（479 条别名；重建时 `bind_alias_table` 实际绑定 471 条，
差额是重复名与既有占用），图谱实体 6815 → 6784（重复节点被合并）。

**两条护栏（都来自本轮实测踩到的真错）**

1. **只信可信名**：取证只用「正名 ∪ 人工别名表里的名字」，**抽取来的别名一律不参与**。
   反例：实体「迈克尔」（NPC Michael）的抽取别名含 `The Fool`，于是灰机命名表把
   **另一个角色**「弄臣」（The Fool）桥到了迈克尔头上；实体「戒指」的别名 `The Ring`
   又把 NPC「圈环」桥了过来。用噪声别名取证 = 把噪声洗成"正典"。
2. **人工裁决不可被自动推翻**：灰机会话产出了 `Kayla += 凯拉`（另有一个 NPC 叫 Kayla），
   而 `docs/plot-graph-rag/corpus/剧情别名与抽取裁决记录.md` 的**裁决 1** 明确「凯拉 / 塞西莉 / 莉莉保留为
   无名者的直接别名」。照单执行会在重建时把「凯拉」改指到 Kayla 节点——那是**推翻
   已记录的人工裁决**，不是数据修复。已在 `HUMAN_RESERVED_ALIASES` 硬拦并写测试。

### 2.5 诚实的失败记录：灰机**没有**的东西

网络核查 17 个「查询里出现、图谱不认」的中文词（伯里克利 / 普帕 / 特蕾西塔 /
穆里尔 / 拉米雷斯 / 摇滚苹果号 …），**只有 3 个**能在灰机找到规范英文名。

- 灰机是**游戏数据维基**（角色数值 / 活动 / 关卡），**没有叙述性条目**；
  `prop=extracts` 对角色页返回 **0 字**（页面正文只有 `{{角色数据}}` 信息框）。
- 上述中文词多来自**国服本地化文本**，灰机并未收录。

→ 结论：**"以灰机为标准"能覆盖命名/章节体系，覆盖不了全部本地化专名。**
剩下的是**真实资料缺口**，不是可以靠调参绕过的检索问题。已如实计入遗留。

## 3. 篇章路由：为「只描述、不点名」的问法开一条通道

用户点名篇章时（「**洞穴的囚徒篇**里海盗船上的歌手是谁」），候选池应缩到该篇文档——
篇章名在**语料元数据**（B 站标题解析出的 `arc`/`chapter`，正典 md 的 `arc`）里是
**精确可匹配**的，跨语言问题在这里不存在。

→ `PlotCorpus.chapter_index()` / `chapters_in()`（长名优先，防「星」吃掉「今夜星光灿烂」）
→ `PlotCorpus.search(doc_ids=...)`（只在给定文档集合内召回）
→ `PlotGraphRetriever` 新增**通道④「篇章」**：不要求图路零命中（点名篇章本身就是强意图），
  作为独立通道参与 RRF 融合，`metadata.path="chapter"` + `chapter_route` 可观测
→ 配置：`plot_chapter_routing` / `plot_chapter_top` / `plot_chapter_max_names` / `plot_weight_chapter`

实测 300 题里约 **150 块**经篇章通道进入结果。

## 4. 两个此前完全没被测量的瓶颈

### 4.1 瓶颈一：**注入预算**，不是检索深度

评测一直只统计「**返回块并集**」的证据覆盖。但产品真正交给模型的是
`build_plot_context(chunks, max_chars=plot_context_max_chars)`——**按名次填、超预算即停**。
于是给评测台加了**注入口径**（`--inject-chars`，默认取生产 Settings）。

| 配置 | 返回块口径 | **注入口径（产品真实口径）** | 实际装入字符 |
|---|---|---|---|
| 原生产：top=3 / 预算 1000 | 47.3% | **37.3%** | 996.9 / 1000 ⟵ **卡死在预算上** |
| top=6 / 预算 2400 | 51.0% | **49.7%** | 2491.5 / 2400 |
| top=6 / 预算 3200 | 51.0% | **55.0%** | 3282.9 / 3200 |

**两条硬结论**：
1. 预算 1000 时平均装入 **996.9 字符**——**预算就是约束**，检索再多也进不去
   （实测 top 6→8 在 2400 预算下**注入结果逐题一致**）；
2. 只看"返回块口径"会**把灌水当提升**：top 3→8 能把返回块口径从 47% 拉到 57%，
   而**注入文本一个字都没变**——那是指标灌水，不是产品变好。

**处置**：`plot_context_max_chars` 1000 → **2400**（+12.4pt），`plot_max_chunks` 3 → **6**。
评测脚本的 `--top` / `--inject-chars` 改成**默认读生产 Settings**，杜绝"评测与生产漂移"。

### 4.2 瓶颈二：**提及通道配额写死 3 块**，多跳题的第 4 块永远进不来

`_mention_channel(targets, per_entity=3, total_cap=6)` 是硬编码。灰机标准题
「在中央塔里自囚的医生是谁」的答案块（**同时含 `central tower` 与 `Aleph`**）
在种子「高塔」名下正排**第 4**，被配额切掉，白丢一组证据。

把这组配额改为可配并消融：

| per_entity / cap | 300 题严格 | 注入口径 | 灰机 14 题 |
|---|---|---|---|
| 3 / 6（旧硬编码） | 51.3% | 50.0% | 12/14 |
| **5 / 10（现默认）** | **53.7%** | **50.3%** | **13/14** |
| 6 / 12 | 53.7% | 50.0% | — |
| 8 / 16 | 53.7% | 50.7% | 13/14 |

### 4.3 顺手修掉的注册表缺陷

`PlotGraphRegistry.get()` 构造检索器时**漏传**了新参数（章节路由/词法档/配额）——
表现为「配置改了没反应」（篇章路由一直是按构造默认值 True 在跑，**关不掉也无法消融**）。
这是比崩溃更难查的一类缺陷，已补齐并加注释。

> 单题量太小（20 题，1 题 = 5pt），不足以判定是真实回退还是抽样噪声。

这是**返回块变多**（4.83 → 7.56 块）的必然结果——该指标的分母是返回块总数，而严格通过率
用的是并集覆盖。两者一起看才有意义：**同样的排序下，多给块提高覆盖、降低"块精度"**。
MRR 0.3284 → **0.3369**（排序质量本身是提升的）。

## 9. M8：跨语言语义检索层（**已建成并启用**，严格通过 +9.6pt）

### 9.1 为什么做

分诊（§1）指出 300 题失败里 **111 题 / 126 组是「别名桥缺失」**——实体在图里，
但查询里根本没出现它的任何名字（「海盗船上的歌手是谁」「雾中女巫」「自囚的医生」）。
补别名**救不了**这类问题：查询与语料之间缺的是"意思"，不是"名字"。
而剧情语料是**英文 ASR**（7964/9021 块），提问是**中文**，图谱
`fingerprint.embedder` 长期是 `none`——**零跨语言兜底**。

### 9.2 建成了什么

| 组件 | 内容 |
|---|---|
| `scripts/build_plot_index.py` | 离线索引构建：批量嵌入 9021 块 + 6784 条实体名；**增量重建**（按 chunk 文本 hash 复用旧向量）；`.npz` 向量 + `.json` 指纹；`--status` / `--probe` / `--crosslingual-check` |
| `src/roleplay/core/knowledge/plot_semantic.py` | `SemanticIndex`：加载、**四项指纹校验**（schema/模型/维度/语料 sha）、余弦检索、实体名向量检索、查询嵌入失败安全返回 `None` |
| `plot_graph.py` 通道⑤ `semantic` | 五路 RRF 融合（edge/mention/**semantic**/chapter/lexical）；查询向量**一次嵌入、两处复用**（块检索 + 实体链接兜底） |
| 实体语义链接兜底 | **精确名匹配全军覆没时**才启用（种子非空就不抢），用实体名向量找回种子——正对"只描述不点名" |
| 配置 | `plot_semantic_enabled/top/weight/link_min/link_top`，默认**关闭** |

**工程约束（本项目踩过的坑，全部落到代码里）**：
1. **指纹优先于可用性**：任一不符即判过期并静默停用——拿旧向量配新模型会静默产出
   垃圾结果，比"没有这一层"危险得多（照搬 HippoRAG 的 index_manifest 思想）；
2. **整层可回滚**：向量与语料物理分离，删 `.npz` 即回到纯图结构/词法世界；
3. **失败必须降级**：文件损坏、维度不符、嵌入服务不可用——四条路径都只告警不抛异常。
   （`tests/test_plotrag_semantic.py` 24 例把这些逐条钉住。）

### 9.3 决定性结论：**必须用多语言嵌入模型**（三组对照实验）

| 嵌入器 | 300 题严格 | 注入口径 | MRR | 延迟 p50 / p95 |
|---|---|---|---|---|
| 语义通道 **OFF** | 53.7% | 50.3% | 0.337 | 137 / 180ms |
| `nomic-embed-text`（英文单语）ON | 50.0%（**−3.7pt**） | 47.0% | 0.287 | 536 / 595ms |
| `nomic` ON + **只留英文块** | 50.0%（−3.7pt） | 47.7% | 0.322 | 558 / 595ms |
| **`bge-m3`（多语言）ON** | **63.3%（+9.6pt）** | **58.0%（+7.7pt）** | **0.386** | 637 / 682ms |

**nomic 为什么不行**：探针实测中文问句「洞穴的囚徒篇里海盗船上的歌手是谁」的 top-4
命中「海因里希 精神不正常」「102房间 地板烧焦」「上好的牛皮笔记本」——
它匹配的是**"这段也是中文"，不是"这段意思相关"**。
第三行是针对性反击：把中文块从候选池剔掉（`plot_semantic_langs=en`）**仍然更差**，
说明该模型跨语言信号本身就不足以在真实 ASR 噪声里排序，不是被中文块挤掉这么简单。

**bge-m3 为什么行**：同一段中文问句，闸门自检的正确/干扰余弦
**0.69–0.82 vs 0.19–0.39**（nomic 是 0.46–0.53 vs 0.51–0.63，方向都是反的）。

**分维度变化（＋语义层带来的第二波）**：multi-hop 25%→**48.3%**｜single 54.5%→**72%**｜
factoid 54.5%→**69.5%**｜reasoning 33.3%→**50%**｜temporal 40%→**70%**｜
easy 62%→**79.3%**｜medium 29%→**49%**｜hard 32%→**44%**｜
天花板内 50.6%→**66.3%**。**每一档都涨**，不是靠某一类题堆出来的。

### 9.4 关键修复：语义通道**必须过种子门控**

第一版把语义通道放在门控之前，结果离题负样本从 **0 块炸到 49 块**
（「今天天气怎么样」「用 Python 写一个快速排序」各被注入 5 块无关转写）——
语义检索什么都不看就能对任何问句返回"最像"的 top-K。

修法与词法兜底同口径（**「剧情层只回答图能认得的问题」**）。**代价只有 2pt**
（+11.6 → +9.6pt），因为分诊显示失败题的种子**几乎总是非空**（只是选错了，
如「洞穴」「海盗」）——门控拦掉的是离题问句，不是目标问句。负样本回到 **0 块**。

### 9.5 副产物：`--crosslingual-check`（上线闸门）

这一步**无法从配置看出来**（`nomic-embed-text` 看起来就是个通用嵌入器），
所以做成了一条可执行自检：用带**中文干扰句**的中→英对齐小题考当前嵌入器。

> 关键细节：**干扰句必须混入中文**。只用英文干扰时 nomic 实测 **4/4 全过**
> （正确 0.46–0.53 vs 干扰 0.31–0.44），看起来"能跨语言"；加入中文干扰才现形。
> 这条闸门后来直接决定了模型选型，**没有它就会把 nomic 当成能用的模型上线**。

```
nomic-embed-text：❌ 跨语言不可用（1/4）   正确 0.46–0.53｜中文干扰 0.51–0.63
bge-m3          ：✅ 跨语言可用（4/4）     正确 0.69–0.82｜中文干扰 0.19–0.39
```

### 9.6 模型是怎么拿到的（环境坑，供后人参考）

ollama 官方拉取通道**在本机不可用**：`bge-m3` 拉了两次都停在 1104MB，
手工落盘的文件**字节数完全正确但 sha256 不符**（并行分片下载留下损坏文件）；
`paraphrase-multilingual` 同样停在 536MB、同样"尺寸对、哈希错"；
`curl` 直连 ollama registry 实测只有 **83 KB/s**（按此速度需约 4 小时）。

**可行路径**：换 **hf-mirror.com** 拉 GGUF（实测 **17.5 MB/s**，417MB 的
`gpustack/bge-m3-GGUF` Q4_K_M 只用了 25 秒），再用 Modelfile 注册进 Ollama：

```bash
curl -L -C - -o bge-m3-Q4_K_M.gguf \
  https://hf-mirror.com/gpustack/bge-m3-GGUF/resolve/main/bge-m3-Q4_K_M.gguf
echo "FROM <绝对路径>/bge-m3-Q4_K_M.gguf" > Modelfile
ollama create bge-m3 -f Modelfile
```

### 9.7 启用配置（本机已生效）

```bash
# .env
ROLEPLAY_PLOT_EMBED_MODEL=bge-m3        # 剧情层专用；全局 embed_model 仍是 nomic
ROLEPLAY_PLOT_SEMANTIC_ENABLED=true
```

**为什么嵌入模型要分两层配置**：全局 `embed_model` 同时被 lore 向量库使用，而 lore 的
向量是按 nomic（768 维）建的——把全局一改成 bge-m3（1024 维）会让 lore 检索整体失配。
`plot_embed_model` 只作用于剧情层，两者互不影响（`factory._build_plot_embedder`）。

**代价（如实记录）**：检索 p50 从 129ms 涨到 **637ms**（查询嵌入约占 430ms），
p95 **682ms**——超出原定 300ms 验收线。权衡：对话主链路紧接着要跑本地 7B 生成
（数秒级），且剧情检索与其余四路检索是 `asyncio.gather` 并行的，实际墙钟增量远小于
508ms。**若要把这 430ms 拿掉**，可选：① 换更小的多语言模型（如
`paraphrase-multilingual`，需重跑闸门与消融）；② 把查询嵌入提前到请求入口、
与其余检索并行预热。

**另一条被排除的路线**：翻译桥（中文查询 → qwen2.5 译英 → 现有英文通道）。
质量够好（「在中央塔里自囚的医生是谁」→ "Who is the doctor who is imprisoning
himself in the central tower?"），但实测 **p50 2.3s（1.5B）/ 2.8s（7B）**，
在线路径不可接受，未采用。

### 10.2 两个"看起来是零、其实不是零"的口径缺陷（本轮实测发现并修掉）

1. **`entity_link_margin` 从未产出过数据**：契约规定 margin 是 AC-3 阈值标定的**唯一**依据，
   而它的采集被 `plot_semantic_link_min > 0` 整体短路，生产该值恰为 `0.0` ——
   字段齐全、数据恒空（与"m=0 是没测到不是没效果"同一类错误）。
   修法：**埋点轮**里无条件打分并落盘 margin，连接行为仍由阈值决定（阈值未配置 ⇒
   不新增种子 ⇒ 检索结果逐位不变；生产不进这段 ⇒ 零延迟影响）。
   首次拿到的真实分布：触发 12 题，margin 全部落在 **< 0.10**（7 题 < 0.02）——
   也就是**纯名字向量下 top1/top2 几乎并列，阈值无从设起**，与 §4e 桶 2 的诊断一致。
2. **`kept_rate` 曾被算成 229%**：契约把「别名精确」定义为**种子来源维度**（§7.6.1），
   它的 `hit_count` 是**种子数**，而 `kept_in_final` 是**块数**。拿种子数当分母、
   块数当分子，得到的不是保留率。修法：新增块级字段 `hit_blocks`（候选块数，
   与 `kept_in_final` 同量纲），保留率一律用它当分母；`squeezed_total` 同理只在
   **块通道**上求和（「别名精确」种子量纲不参与），并把规格原文公式的逐字复算值
   一并落盘（`squeezed_total_literal_spec_formula`）以便审计——改口径不能悄悄改。

  `cases_executed`=255 —— 功能**确实被测到**，这是"测到了但无正收益"，
  不是"没测到"（两者在报告里必须区分，§7.6.6）。
- **C4（手工边豁免）：保留 Spec 锁定默认值**。m=0（逐题判定完全一致），
