## 摘要：四条的结论方向

| 缺口 | 外部共识 | 我们的落地 |
|---|---|---|
| G1 池宽 vs 输出数 | 成熟框架**全部**拆成两个参数 | `top_k` 只控输出，新增 `pool_top_n`（ES `rank_window_size` 语义） |
| G2 向量阈值 | 是**可选过滤**，不是必须项；绝对阈值有「全空」前科 | 加 `min_score` 但**默认 `None` 关闭**，阈值必须从本仓库分布标定 |
| G3 端点实体 | 主流把「实体是关系端点」当**一等命中** | `_count_mentions` 补②端点段；**明确不宣称召回提升** |
| G4 dangling 质量 | 教科书与所有实现都**回流 teleport** | `damping*dangling` 按 teleport 向量分配，不再按节点数均摊 |

## G1 — 池宽与输出数：两个参数的词汇分化

### 外部做法

**Elasticsearch RRF**（最直接先例）
`rrf` retriever 上有 `rank_window_size` 与 `size` 两个独立参数：
`rank_window_size` = 每路查询**进入融合的候选数**，`size` = **最终返回条数**。
官方文档明确「最终结果集被裁剪到 `size`」，且约束 `rank_window_size >= size`。
这是本仓库缺的那个词汇分化——我们有 `size` 的语义，却拿它当 `rank_window_size` 用。

**LlamaIndex**
`similarity_top_k` 是**召回池**；裁剪交给后处理器
（`node_postprocessors=[LLMRerank(top_n=…)]` / `SimilarityPostprocessor`）。
默认心智模型就是「召回宽、输出窄」。

**LangChain**
`EnsembleRetriever` 内部各路 `search_kwargs={'k': …}` 是池；
`ContextualCompressionRetriever(top_n=…)` 是输出；MMR 另有 `fetch_k` 与 `k` 之分。

**Haystack**
`InMemoryBM25Retriever(top_k=…)` 之后接 `DocumentJoiner` / 顶层 `top_k` 截断，同样是两段。

### 对我们的约束

1. **`top_k` 必须只表示输出条数**。继续让它兼职池宽，任何调用方都无法表达
   「宽召回 + 窄输出」，而这恰是重排/影子实验的刚需。
2. **默认值必须复现旧行为**：旧公式是 `max(top_k*4, 24)`，所以 `pool_top_n=None`
   → 走同一公式。这样存量调用零改动、读数可比。
3. **全池要有出口**：诊断脚本要的是整个池，不是前 6 条。故新增 `evidence_pool`
   （默认 `None`，不进 `to_dict()`，避免工件膨胀）。
4. **唯一硬依赖**是 `scripts/compendium_rag_p8_roleiso_shadow.py`——它的 docstring 写明
   「必须逐字复刻原 harness，否则读数不可比」，所以它是**必须显式传参**的那个。

### 本仓库实测（缺口存在性的证据）

现有工件里每查询返回的证据数：**k1c300 最小 33 / 中位 68 / 最大 105**。
即 `top_k=6` 名义上返回 6 条，实际返回 33–105 条。这不是理论缺陷，是产线可见的。

## G2 — 向量相似度阈值：可选过滤，且必须自标定

### 外部做法

| 系统 | 机制 |
|---|---|
| **Qdrant** | `score_threshold` 是 search/recommend 的一等参数：低于阈值的结果不返回 |
| **FAISS** | `range_search(radius=…)` 提供半径过滤；`IndexFlatIP` 需先归一化，否则「相似度」不是余弦 |
| **pgvector** | `hnsw.ef_search` 控候选、`hnsw.iterative_scan` 控过阈值后的补量 |
| **Chroma** | `distance = 1 - cosine_similarity`，可 >1，需换算后才能当阈值用 |

### 关键反例（决定了我们的默认值）

**LightRAG 曾引入 cosine threshold，后又移除**：
`271df99`（fix/cosine-threshold-empty-env）、`2b52d43`（remove deprecated cosine threshold field）。
原因正是**绝对阈值容易造成「全空」副作用**——一旦某查询的所有候选都低于阈值，
检索直接返回空，下游全崩。

⇒ **推论：阈值必须默认可关，且关掉后行为与改造前字节级一致。**
这就是为什么 `Settings.retrieval_vector_min_score` 默认 `None` 而不是某个「看起来合理」的数。

### 被证伪的阈值来源

**BGE 模型卡 FAQ 说相似度分布落在 [0.6, 1]，并要求用户用自己的数据选阈值。**

本仓库实测（**不适用**模型卡那个区间）：

> `data/compendium_rag/reports/rank_collect_k1c300_top30.json` 携带的 vector 原始 cosine，
> n=4578：**min 0.3178 / p10 0.4247 / p25 0.4558 / median 0.4973 / p75 0.5357 / max 0.6571**
>
> ⇒ 整个分布落在 **0.32–0.67**，中位数 ≈ **0.50**。
> **直接套 0.6 会砍掉约一半证据**（0.6 已接近 max 0.6571）。

所以：**任何阈值必须从本仓库工件的实测分布标定**，`p10 = 0.4247` 是「砍掉最弱 10%」
的候选点，但仍需 eval300 验证 hit@6 / MRR 不退化才允许采用。

### 对实现的两条硬约束

1. **过滤必须在截断之前**。若先取 top-30 再过滤，等价于「在 30 条里删掉弱的」，
   语义是错的——正确语义是「在全库里选过阈值的，再取前 N」。
   实现：`keep = np.flatnonzero(sims >= min_score)` 再截断。
2. **keyword 兼容**：现有 16 处脚本都按位置参数调用 `vector_channel(qvec, top_k)`，
   所以 `min_score` 只能是可选的 keyword 参数，不能插到位置参数中间。

## G3 — 关系端点实体：两条流派，本仓库原先两头不靠

### 流派一：实体候选由**向量召回**决定（Microsoft GraphRAG）

`local_search` 的入口是「查询 ↔ 实体描述」的向量检索
（`_map_query_to_entities` → `_build_entities_from_rows`），
再按 `top_k_entities` / `top_k_relationships` 展开邻域。
**实体候选完全不依赖 mention 计数**，所以天然免疫本仓库 G3。

### 流派二：实体权重来自 **NER 命中 + PPR**（HippoRAG / HippoRAG-2）

实体节点权重来自 NER 命中与 `personalized_pagerank`，图的边是**共现**。
端点实体本身不额外计提及——因为「共现边」这个建模里，端点和声明本就没有区别。

### 流派三：实体向量/keyword 召回后取其在 chunks 中的出现（LightRAG `local`）

同样把「实体的 chunk 出现」当成实体的一等属性。

### 共同点与我们的位置

> **所有主流做法都把「实体是关系端点」当作一等命中**，
> 不会因为某实体只作 `src`/`dst` 就被判为低分。

本仓库原先：实体入口是**名字逐字匹配**（`link`），展开走 `mention_channel`
读 `ent.chunk_ids`。而 `chunk_ids` 只由**块内显式声明**产生
→ 「只作端点出现」的实体在那些块上是**永久盲区**。
这既不是流派一的「向量召回」，也不是流派二的「共现边」，而是**契约不对称**。

### 但修复的收益必须诚实度量（本条最重要）

补上端点段之后，在**真实工件**上只新增 **11 个 (entity, block) 对**、
只影响 **1 个实体**（店主），且**零个实体的 `chunk_ids` 为空**
（`g3_blind_report.json`）。

更要紧的是：把「工件陈旧度」和「本轮改动」拆开量之后
（`drift_split.json`，同一份 chunks+cache，只切 G3 开/关）：

| 对比 | 含义 | 结果 |
|---|---|---|
| A vs B | 工件 vs 改动前代码重建 | 6 个实体 `chunk_ids` 变、840/583 条边差异 → **陈旧度** |
| **B vs C** | **改动前 vs 改动后代码** | **全零**（实体 0、边 0、chunk_ids 0、mentions 0） |

原因：`extract.py:299-335` 已强制每个关系端点解析到同块实体名/别名/说话人，
所以当前抽取管线里**不存在「纯端点实体」**，②段是纯 no-op。

> **结论：G3 是契约正确性修复，当前召回收益 ≈ 0。**
> 立项理由必须是「契约对称 + 可重建」，**不得包装成召回提升**。
> 这正是外部对照给出的教训：流派一的范式才是真正解决盲区的路（改入口），
> 而不是补一条计数规则。补计数只是**消除不对称**，不是**提升召回**。

### 风险点：`cids[:per_entity]` 的顺序敏感性

`mention_channel` 取 `cids[:3]`。追加端点块会改变 `chunk_ids` 内容，
若顺序还随插入序漂移，截断结果就会漂移。全图有 3945 个实体**恰好 1 个 chunk_id**，
`chunk_ids` 少于 3 的实体会直接受影响。
⇒ 必须同时做**顺序确定化**（按 `(块在语料中的序, chunk_id)` 排序）。
只改内容不定序，等于把一个隐蔽的不可复现性引入产线。

## G4 — dangling 质量：教科书级的唯一正确答案

### 外部做法（两边完全一致）

**NetworkX `pagerank`**
有显式 `dangling` 参数，默认语义：dangling 节点的出边质量**按 personalization 向量分配**。

**igraph `personalized_pagerank`**
实现式：

```
pr_new[v] = (1 - damping) * norm_reset[v]
          + damping * (incoming[v] + dangling_sum * norm_reset[v])
```

源码注释原文：**「Dangling nodes also distribute according to norm_reset.」**
其测试 `isolated_vertices_with_biased_reset` 断言：孤立节点的 reset 为 1.0、其余为 0，
**且孤立节点保留全部质量**。

### 本仓库的错法，以及它为什么是「最严重」的一条

错法：`share = damping * dangling / len(nodes)`，均摊给全图。

后果（本仓库实测，`data/compendium_rag/graph.json` 7033 实体 / 27110 边，
`build_adjacency` 产出 5900 节点，**其中 1133 个孤立**，占 19.2%）：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| `edges sc>0` | 27110（**全部**） | **0** |
| top-30 边裁剪产出块 | **91 个无关块** | **0** |
| `nonzero` 节点 | 5901（全部） | **1** |
| `seed_score` | 1.0 | 1.0（语义不变） |

均摊的直接效果是：**任何一个孤立种子都会产出 91 个完全无关的块**，
且所有孤立种子（1914军事基地 / 22#0 / APPLeⅡ号 / G33针管 / K.U.K. …）
分数**完全相同**（0.000299…–0.1742 的同一组数），查询毫无区分度。
这不是「差一点」，是把噪声当证据注入 RRF。

修复后语义：孤立种子 → 图通道**零命中** → 自然回落词面/向量通道。
这是正确的「零命中」语义。同时确认连通图未退化：
正常种子下 `nonzero=5790`、`edges_with_positive_score = 27043 / 27110`。

### 外部对照给出的额外要求

igraph 的实现把 dangling 分配**叠在** `(1-damping)*norm_reset` 之上，
而不是替换它。我们的实现也遵循这一点：`nxt` 初始化时已含
`(1.0 - damping) * teleport.get(n, 0.0)`，之后再 `+= share * tp`。
**不要**把 dangling 分摊写成覆盖式赋值，否则 teleport 项会被吃掉。

## 横向教训（四条合起来看）

1. **参数语义要分化，不要兼职**（G1）。`top_k` 兼池宽 = 调用方无法表达意图。
2. **新过滤能力默认关闭，且关闭路径必须逐位复现旧行为**（G2）。
   有绝对阈值前科的框架（LightRAG）已经证明了这一点。
3. **阈值/超参必须从自己的数据分布标定，不要抄模型卡**（G2）。
   BGE 的 [0.6,1] 与本仓库的 [0.32,0.67] 差了一整个可用区间。
4. **契约不对称 ≠ 召回缺陷**（G3）。补齐契约是对的，但别宣称性能提升；
   真正的召回改进要改入口范式（向量召回实体），那是另一件事。
5. **数值算法要按教科书写**（G4）。dangling → teleport 是唯一正确答案，
   均摊是纯粹的 bug，且它污染的是「本来就没有证据」的查询——
   这类查询恰恰最不该被注入噪声。
