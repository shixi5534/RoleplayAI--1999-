# 「以灰机为标准补名」路线 —— 灰机实证与判决

> 本轮**只读**：未改 canonical 数据、未改检索代码、未覆盖任何既有报告；
> 临时探针全部删除，`HEAD` 仍为 `1c8aa15`。

## 1. 一句话结论

**「以灰机为标准补名」救不了 native 的主要失分——卡点是灰机的数据模型，不是实现力度。**

灰机正典是**命名词典 + 词条描述**，**没有任何带类型的关系数据**；
而 native 250 题里 **66%（166 题）是关系题**（「谁告知了「维尔汀」？」），
答案在**关系的另一端**，灰机对此**结构上无话可说**。
唯一可能受益的是 T2 定义题（33%），实测**打平到负**。

**本轮真正的意外收获不在灰机，而在图通道**：把查询里已出现的关系词用于给边加权，
native 端到端 **0.6320 → 0.7080（+7.60pt，19 涨 0 跌）**。
⚠ 但它有**测试集循环性**嫌疑，见 §5——**不要直接当成用户侧收益**。

## 2. 先钉死上界：补名到底能拿多少（oracle）

把该题期望答案词直接拼到 query 后（= 识别器 100% 全对）：

| 题集 | 现状 hit@6 | oracle 拼答案 | 恢复 | Δ | 提升后 |
|---|---|---|---|---|---|
| 300_cn answerable(196) | 0.8010 | +24/39 miss | — | **+12.24pt** | **0.9235** |
| **native(250)** | 0.6320 | **+85/92 miss** | — | **+34.00pt** | **0.9720** |

⇒ 上界巨大且**是native 的第一大杠杆**，与历史 plot 侧「补名上界 +28~+36」同源。
⚠ 这是在 **miss 子集**上算的，属投影；下面所有「可落地形态」都按**全量**口径报。

**关键分流**：再测一个零 LLM 的「只补题面已出现实体的别名」（不需要猜答案）：

| 题集 | 零LLM 补已知别名 | 结论 |
|---|---|---|
| 300_cn | **+7/39（+3.57pt）** | 小正 |
| native | **+1/92（+0.40pt）** | **几乎为零** |

⇒ **收益必须来自「猜出答案实体」**，而不是「补全已知实体的其它写法」。
这决定了灰机能不能派上用场：灰机得能**推出答案是谁**。

## 3. 灰机能提供什么（实测清点）

`data/lore/wu_ming_zhe/huiji_canon.json`（灰机离线正典，1428 个去重写法）：

| 段 | 条数 | 字段 | 有没有关系信息 |
|---|---|---|---|
| `characters` | 141 | `{zh, en, page}` | ❌ 只有名字与页面链接 |
| `npcs` | 184 | `{zh, en, identity, version, arc, page}` | ❌ `identity` 是身份备注（65/184 非空），不是关系 |
| `name_table` | 576 | `{zh, en, kind, page}` | ❌ 纯名词表 |
| `terms` | 25 | `{displaytitle, plain, links, url}` | ⚠ **仅 21/25 页**有 `links`，且是**无类型的页面共现**，不是「A 告知 B」这种有向关系 |

**两个硬数字：**

- 灰机 1428 个名字里，**只有 276 个（19.3%）能被 compendium 图谱 `resolve()`**；
  反向地，图谱 7033 个正名里只有 **255 个（3.6%）出现在灰机**。
  ⇒ 两套命名体系**大部分不重叠**，灰机不是这个库的上位词表。
- 灰机**不存在**「关系 → 实体」的映射。native 的关系题问的正是这个。

## 4. 灰机补名的实测（全量口径）

实现：建灰机描述索引（926 条）→ 查询向量找最近灰机实体 → 把该实体名拼进 compendium 查询。

| 题集 | 现状 | 灰机补名 | Δ | 涨 / 跌 |
|---|---|---|---|---|
| 300_cn | 0.8010 | 0.7959 | **−0.51pt** | 6 / 7 |
| **native** | 0.6320 | **0.5440** | **−8.80pt** | **1 / 23** |

**native 上 23 题被砸掉、只救回 1 题。** 机理清楚：盲猜的灰机实体**大概率不是答案**，
把一个**错实体**拼进查询 = 往查询里灌噪声，把原本能覆盖证据的块挤出去
（与历史「PRF 伪反馈 −2~−9pt」「同义改写 inject −3」同一病：**往查询里加错东西**）。

**判决：灰机描述索引补名，作为召回杠杆不成立。**

## 5. 意外收获：关系感知的图通道加权（全量端到端）

### 5.1 动机

native 的 T1r 题是「谁**告知**了「维尔汀」？」——题面**给了实体 A 和关系词**，问另一端 B。
而 `graph_channel()` 的打分是 `(ppr[src]+ppr[dst]) × max(0.1, conf)`，
**完全不看用户问的是哪个关系** → A 的几百条边一视同仁地竞争那 30 个名额。
这正好解释了报告 §7 的观测「失手题更集中在枢纽（`维尔汀` DF=826）」。

### 5.2 实测（真端到端，无重放）

把「查询里出现的关系词」作为额外信息给匹配的边加权：
`sc = base × (1 + bonus × 1[relation ∈ query])`。

**有效性自检**：`bonus=0` 必须逐位等于已存档基线。**两套题都逐位复现**
（native `0.6320/0.6320`，300_cn `0.8010/0.8010`，up=0 dn=0）⇒ 本测量有效。

| 题集 | bonus=0 | bonus=1.0 | Δ | 涨 / 跌 |
|---|---|---|---|---|
| **native** | 0.6320 | **0.7080** | **+7.60pt** | **19 / 0** |
| 300_cn（人工题对照） | 0.8010 | 0.8061 | +0.51pt | 1 / 0 |

native 分题型：`T1 58/84 → 68/84`、`T1r 60/83 → 66/83`、`T2 40/83 → 43/83`。
**bonus 0.5 到 4.0 结果完全相同**（关系匹配是布尔量，只要大于 0 排序就一样）。

### 5.3 ⚠ 致命保留：测试集循环性

**native 的 T1/T1r 题面是脚本用图谱自己的关系串逐字模板化生成的**
（`_gen_native_qa.py`：`f"「{a.name}」{rel}的对象..."` / `f"{who}{rel}{tail}「{a.name}」？"`）。
实测题面**逐字包含某个图谱关系词**的比例：

| 题型 | 比例 |
|---|---|
| native **T1** | **84/84 = 100%** |
| native **T1r** | **83/83 = 100%** |
| native T2 | 61/83 = 73.5% |
| 300_cn（人工题） | 168/300 = 56.0% |

⇒ **native 上测到的 +7.60pt 里，绝大多数是「查询串与图谱关系串逐字对上」的产物。**
证据链自洽：增益集中在 T1/T1r（+10 / +6），而**真正自由文本**的 T2 只有 +3；
换到**人工撰写的 300_cn**，同一改动只有 **+0.51pt（1 题）**。

**真实用户不会说图谱内部的那个动词**（用户会说「谁告诉维尔汀的」，
图谱里存的是「告知」）。所以**不能把 +7.60pt 当作用户侧收益**——
它是「测试集与图谱同源」的测量假象，属于本项目已登记过的**口径污染**类问题
（同类：T5 摘要节点 +22 被证为灌水）。

### 5.4 这条线索的真正价值

不是那个数字，而是它指出一个**真实且未被处理**的检索缺陷：
**关系词被完全忽略**。要让它对真实用户生效，需要一个
**关系词的近义归并表**（「告知/告诉/通报/知会 → 告知」），
而不是拿 8352 个关系串做子串匹配。这是一个**独立的、可验证的**小工程，
验收口径必须是**人工撰写的题集**（300_cn 那一类），**不是 native**。

## 6. 判决与建议

| 形态 | 全量实测 | 判定 |
|---|---|---|
| oracle 拼答案（上界） | native **+34.00pt** / 300cn +12.24pt | 诊断资产，说明空间真实 |
| 零 LLM 补已知实体别名 | native +0.40pt | 无效 |
| **灰机描述索引补名** | native **−8.80pt**（1 涨 23 跌） | ❌ **否决** |
| 关系感知边加权 | native +7.60pt / 300cn +0.51pt | ⚠ **疑似循环性污染，须重测** |

**核心判决：`以灰机为标准补名` 这条路，被灰机的数据模型堵死。**
灰机可以补「名字」（19.3% 可解析），补不了「关系」；而 native 的失分主体正是关系题。
要推进补名，只有 §7 的两条，都**不依赖灰机**。

## 7. 「补名」还能怎么走（不依赖灰机）

1. **关系词近义归并表**（承接 §5.4，成本最低）
   产出：`关系串 → 规范关系` 映射 + 图通道按规范化关系匹配。
   验收：**300_cn 一类人工题**上 hit@6 提升，且 native 的虚高数字**不得**作为依据。
   风险：这张表本身需要语料统计支撑，不能拍脑袋。

2. **强模型实体识别**（历史唯一大赢家族）
   前置：有效 LLM key（现 `.env` 是 `ollama` 占位，实测 401）。
   依据：plot 侧实测 +18~+23pt；上界见 §2（native +34pt）。
   形态：**离线预生成映射 + 在线查表**，否则在线延迟不可接受。

**明确不要做**：把灰机（或任何外部词表）盲猜的实体名直接拼进查询——
本轮 native −8.80pt 已经把这条路封死了。

## 8. 复现要点（三个探针，已删除，形态记录于此）

1. **oracle 上界**：`q_aug = q + " " + 期望答案词` → 重检索 → 看 top-6 是否命中。
2. **灰机补名**：灰机 `characters/npcs/name_table/terms` 拼描述文本 → bge-m3 嵌入
   （926 条，本地 Ollama）→ query 向量取 top-1 → 实体名拼进查询 → 重检索。
3. **关系加权**：覆写 `GraphRetriever.graph_channel` 内部打分
   `sc = base × (1 + bonus × 1[relation ∈ query])`，**再按原逻辑 `[:max_edges]` 截断**
   （不截断会破坏保真：先前重放版 bonus=0 复现不出基线，就是这个原因）。
   **自检闸门：`bonus=0` 必须逐位等于 `eval_*_after_welds.json`**，否则测量无效。

**方法论教训（本轮第三次踩到）**：任何改「通道字典/排序」的参数，
**必须在全量上量、并且先证明零档能逐位复现基线**；
只看 miss 子集或不做零档自检，得到的数字连符号都可能是错的。
