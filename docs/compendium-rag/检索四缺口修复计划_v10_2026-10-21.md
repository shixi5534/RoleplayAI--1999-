## 1. 外部同类项目的做法（研究结论，均为 github/官方文档实测引用）

### G1 —— 池宽 vs 输出数：所有成熟框架都拆成两个参数
- **Elasticsearch RRF**：`rank_window_size`（进入融合的每路候选数）与 `size`（最终输出数）是两个独立参数，文档明确「最终结果集裁剪到 `size`」，且约束 `rank_window_size >= size`。这是本仓库缺的那个词汇分化的直接先例。
- **LlamaIndex**：`similarity_top_k` 是召回池，裁剪交给 `node_postprocessors=[LLMRerank(top_n=…)]` / `SimilarityPostprocessor`——**召回宽、输出窄是默认心智模型**。
- **LangChain**：`EnsembleRetriever` 内部各路 `search_kwargs={'k':…}` 为池，`ContextualCompressionRetriever(top_n=…)` 为输出；MMR 另有 `fetch_k`。
- **Haystack**：`InMemoryBM25Retriever(top_k=…)` 后接 `DocumentJoiner`/`top_k` 截断，同样是两段。
- **结论**：`top_k` 必须只表示「输出条数」，池宽需另起名（本计划取 `pool_top_n`，ES 的 `rank_window_size` 语义）。

### G2 —— 向量相似度阈值：是「可选过滤」而非「必须存在」
- **Qdrant**：`score_threshold` 是 search/recommend 的一等参数（我们已确认的官方语义：低于阈值的结果不返回）。
- **FAISS**：`range_search(radius=…)` 提供半径过滤；`IndexFlatIP` 需先归一化，否则「相似度」不是余弦。
- **pgvector**：`hnsw.ef_search` 控候选、`hnsw.iterative_scan` 控过阈值后的补量。
- **Chroma**：`distance = 1 - cosine_similarity`，可 >1，需换算。
- **重要反例**：**LightRAG 曾有 cosine threshold 后来移除**（commit `271df99` fix/cosine-threshold-empty-env、`2b52d43` remove deprecated cosine threshold field）——说明绝对阈值容易造成「全空」副作用，必须**默认可关、且关掉不改变现有行为**。
- **BGE 模型卡 FAQ 说分布落在 [0.6,1] 并要求用户用自己的数据选阈值**——已核实：本仓库 bge-m3 中文语料实测分布是 **0.32–0.67，中位数 ≈0.50**，直接套用 0.6 会把一半证据砍掉。阈值必须**从本仓库工件的实测分布标定**（`data/compendium_rag/reports/rank_collect_k1c300_top30.json`、`rank_collect_v6c300_top30.json` 携带的 vector 原始 cosine：k1c300 n=4578 min 0.3178 / p10 0.4247 / p25 0.4558 / median 0.4973 / p75 0.5357 / max 0.6571）。

### G3 —— 提及通道/端点实体：两条流派
- **Microsoft GraphRAG local_search**：实体入口是「查询 ↔ 实体描述」的向量检索（`_map_query_to_entities` → `_build_entities_from_rows`），再按 `top_k_entities`/`top_k_relationships` 展开，**实体候选由向量召回决定，不依赖 mention 计数**——这天然免疫本仓库 G3。
- **HippoRAG / HippoRAG-2**：实体节点权重来自 NER 命中 + `personalized_pagerank`，图的边是共现，端点实体本身不额外计提及。
- **LightRAG local retrieval**：实体按向量/keyword 召回后，取其在 chunks 中的出现。
- **共同点**：主流做法把「实体是关系端点」当作**一等命中**，不会因为该实体只作 src/dst 就被判为低分。本仓库 `_count_mentions` 只看 block 内声明，是**契约不对称**。

### G4 —— dangling 质量：教科书与所有实现都回流 teleport
- **NetworkX `pagerank`**：显式 `dangling` 参数，默认「dangling 节点的出边按 personalization 向量分配」。
- **igraph `personalized_pagerank`**：`pr_new[v] = (1-damping)*norm_reset[v] + damping*(incoming + dangling_sum*norm_reset[v])`，注释原文「Dangling nodes also distribute according to norm_reset」；其测试 `isolated_vertices_with_biased_reset` 断言孤立节点上 reset 为 1.0、其余为 0。**这正是本仓库 PPR 该有的行为而没有**。
- **结论**：`daming*dangling` 必须按 `teleport` 向量回流，而不是 `len(nodes)` 均摊。

## 2. 实测事实（本会话在真实工件上量出来的，不是估算）

### G4（最严重）
- 图：`data/compendium_rag/graph.json` = 7033 实体 / 27110 边；`build_adjacency` 产出 5900 节点，**1133 个孤立节点**。
- 现状：单孤立种子 PPR → `nodes_scored=5901 nonzero=5901 max=1.0`，且**全部 27110 条边 `sc>0`**（0.000299…–0.1742）。任何孤立种子（1914军事基地 / 22#0 / APPLeⅡ号 / G33针管 / K.U.K.）数值完全相同，于是 top-30 边裁剪变成**全图随机置信度抽取**，`graph_channel` 产出 **91 个无关块**。
- 修正后：同种子 → `edges sc>0 = 0`、`top30 chunk = 0`、`nonzero nodes = 1`、`seed_score = 1.0`。即孤立种子查询不再产出图证据（自然回落到 lex/vector 通道），这是正确的零命中语义。

### G3
- 把关系端点计入 `_count_mentions`：全图只新增 **11 个 (entity, block) 对**，只影响 **1 个实体**（店主，mentions 3→有 chunk_ids 覆盖 11 个原本盲区的块，全部在 `anecdote__1917_乘法轴上的一天` 下）。
- **零个实体的 chunk_ids 为空**——本版本不存在「纯端点实体」。根因是跨块的正名/别名合并，不是端点未校验（`extract.py:299-335` 已强制每个关系端点解析到同块实体名/别名/说话人）。
- ⇒ **诚实结论：G3 是契约正确性问题，当前召回收益 ≈ 0**。必须按「正确性修复 + 可重建」而非「召回提升」立项，且不可宣称性能改善。
- 修复可从本地 cache 免费重建（`NORMALIZER_VERSION="n2"`、`PROMPT_VERSION="v3"`、cache 存 RAW 输出、`cache_key` 不含 normalizer）——**无云端成本**。
- 风险点：`mention_channel` 取 `cids[:per_entity]`（per_entity=3）是**插入序**，追加端点块只改变 chunk_ids 少于 3 的实体（3945 个实体恰好 1 个 chunk_id），影响有界但非零，顺序必须确定化。
