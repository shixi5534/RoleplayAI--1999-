## 3. 核心发现：RRF 的 k 常数（前序只扫权重，未扫 k）

`rrf_fuse`：`score = Σ_ch w_ch × 1/(k + rank_ch)`。

| k | rank1 | rank6 | 头名相对第 6 名 |
|---|---|---|---|
| 60（历史） | 1/61 = 0.0164 | 1/66 = 0.0152 | **1.08×** |
| **1** | 1/2 = 0.500 | 1/7 = 0.143 | **3.50×** |

k=60 时"排第 1"与"排第 6"几乎等价 ⇒ **单通道霸榜**可压过**多通道共识**。
k 调的是**名次折扣曲线**；而前序扫的**权重**只是全局缩放，
**不改通道内相对名次**，故对"深排名候选"无效 —— 这解释了
`目标①_池内miss干预报告` 里"六类调参全部否决"的原因，也指明了真正的杠杆。

## 4. 方法学（本轮新增纪律）

1. **先证明离线工具同源，再扫参**：
   - `_85_validate_rrf.py`：用 `reasons` 重建 score，**2400/2400 精确一致**；
   - `_85_validate_replay.py`：离线重放对 v6/`lex_first=3` 四配置**逐题一致**。
   未做这两步之前，任何扫参结论都不可信。
2. **k 只在 300cn 上选，盲测为留出集**（沿用既有纪律）。
3. **最终必须真冷启动复核**：离线重放器只能重排既有池内的块，
   而 k 会改变**池的构造**，故离线值只是预测，须以真 eval 为准（本轮实测两侧一致）。
4. **单参数优先**：k 是**一个全局常数**；相比之下 `lex_first` 是另一套结构改动，
   且与重排交互为负。在都能达标时选**参数更少、生产口径不回退**的方案。

## 6. 工程坑（继承 + 本轮）

- **`Select-Object -Last N` 会缓冲到进程结束**：长任务看不到进度，
  改用「日志写文件 + `Get-Content -Tail`」或 `python -u`。
- **多进程竞争 CPU 会显著拖慢 PPR 评测**：本轮一个子代理与主评测并行，
  使 300cn 单集评测从 ~20 分钟涨到 ~50 分钟。长评测期间不宜并行重活。
- 继承：`data/` 在 gitignore 内需 `git add -f`（**且要逐条精确路径**，
  `git rm -r --cached` 曾误暂存 5087 个删除）；**不要**用 PowerShell
  `Set-Content -Encoding UTF8` 改中文源码（会 mojibake）；文件内容以 Python 直读为准。
